## The plan picture production refused (T-684)

The v1.0 release lead found that production refused the planner's plan picture: Send to Events Team uploaded an
800×533 PNG, `POST /public/configurations/:id/thumbnail` answered 400 (its cap is 270,000 characters), and the send
went on without a word. The sheet PDF prints that picture only for a layout saved with no plan; for a layout with
one it draws the saved plan itself (`sheet-pdf/blocks.ts`, planner-qol E-X4), so the paper was not affected. The
cost was a refused upload of some 685 KB on every send, which the guest waits for before the enquiry opens, and no
picture kept with the layout.

- Measured in Chrome (WebGPU) on the planner lab's Grand Hall (160 guests, sky off; frames and report in
  `D:/claude/webgpu-target-safe-mrt/thumb/sky0-day/`): as PNG the plan is 513,994 bytes, a 685,350-character data
  URL; as JPEG at 0.85 it is 72,314 bytes, 96,443 characters, 173,557 under the cap (the cap is 2.8 times it).
  Against the PNG of the same frame the JPEG is 35.3 dB PSNR (a mean 2.4 of 255; 0.01% of pixels more than 48 off
  in a channel, at edges). Every pixel's alpha is 255, so a JPEG's lack of alpha changes nothing, and the tables'
  labels read cleanly.
- `PLAN_THUMBNAIL` (web `lib/ortho-capture.ts`) is the plan Send to Events Team captures: JPEG at 0.85, stepping
  down to 0.75, 0.65 and 0.55 for a plan that does not fit, otherwise no image. Submit for Approval's capture runs
  only for a public preview, and its panel shows only for signed-in layouts, so in practice it uploads nothing. A readback of one colour, a draw that drew
  nothing, gives no image: no plan beats a blank one (#339's review).
- The route took PNG data URLs only, by their label. It now takes PNG or JPEG, requires every character after the
  prefix to be plain padded base64 (so nothing but the image is stored, and the cap is 270 KB), and checks that the
  decoded first bytes match the declared type (PNG's eight-byte signature, JPEG's FF D8 FF); mislabelled payloads,
  WebP, URL-safe or broken base64 and junk get 400. The cap, the rate limit and who may write (a public preview, unclaimed, not deleted, not locked for
  review, all re-checked in the UPDATE) are unchanged. Every reader of `thumbnailUrl` takes JPEG: the sheet PDF's
  `diagramBytes` takes any `data:image/` URL and pdfkit embeds PNG or JPEG; the snapshot and review schemas check a
  URL, not a type (zod 4.6.7's `z.url()` takes the 96,443-character JPEG unchanged); no web page or email renders it.
- The API's test posts that exact capture (`packages/api/src/__tests__/fixtures/grand-hall-plan-thumbnail.jpg`), and
  the web test reads the route's cap from its source, so the two cannot drift apart unseen.
- A plan image that never reaches the layout is now reported (`plan-image-failed`, once per page, tags only: the
  stage, and an upload's HTTP status, "network", or "response-shape" for a reply the client could not read); the
  send still goes on, as before.
- The clearance lines (the circulation overlay) stay out of every plan (#339's review). Asked whether a blocked
  door's warm-gold warning should appear in the plan the venue receives, Blake chose "Show it (Recommended)", so it
  stays in.
- With `?sky=1` at 18:00 the first capture after load drew blank: the glass, street beams and halos failed to
  compile (T-682's empty `OutputType` struct, fixed by #339, which this branch did not yet have), and the guard sent
  no plan instead of a blank one. A PNG captured straight after did draw, at 820,410 characters.
- An independent review (five lenses, each finding put to two skeptics; 10 confirmed, 1 refuted) found the same
  dependency for the door warning: on WebGPU a blocked door's pool and edge write the scene pass's outputs, so, by
  the code, a capture with a piece in a door's clear space comes back blank before #339 and sends no plan. T-684
  therefore lands on #339. It also found the over-cap test no longer isolated the cap, text after a valid signature could be stored,
  an unreadable reply was tagged "network", and comments and docs overstated what the sheet and Submit for Approval

## What X's rebuild of x.com suggests for us (T-685)

Blake, sharing X Engineering's "Rebuilding the global town square from scratch" (4 Nov 2026): "is there anything
they have said that could give us ideas on how to improve our own performance in any capacity/area". The answer, its
evidence and the ranked ideas are in `D:/claude/x-perf-20261105/REPORT.md`: an eight-area audit of origin/master
f47fdbe6 with adversarial verifiers, plus live checks of venviewer.com and api.venviewer.com.

- **The database no longer sleeps (Blake's choice, about $19 a month).**
  - Neon suspended the production compute (`ep-dawn-glitter-abx2ux6f`) after 5 idle minutes. The next visitor
    waited for it: the same public `GET /venues` took 2.83 s asleep and 0.18 s awake. Sentry's first-after-idle
    samples were 0.8-1.5 s, against 25-50 ms warm.
  - Set to never suspend (`suspend_timeout_seconds: -1`) at 10:30 UTC.
  - Afterwards the first request after a 95 s lull took 0.12 s and 0.22 s, with a fresh pool connection each time.
    So the cost was the compute waking, not the API's 60 s pool idle timeout. The first request after a compute
    restart (Neon's maintenance window, Sundays 03:00-04:00) can still take about 3 s.
- **Measured on the live build.**
  - The front door starts 20 files, 182 KB brotli.
  - `/plan` preloads 80 files, 1.30 MB brotli (EditorPage 432 KB, both three.js builds 495 KB), before its first
    API call. It then reads venues, rooms and the new draft in series.
  - Opening `/plan` creates a production draft, so lab runs of the planner must block writes. The measurement
    script does: `D:/claude/x-perf-20261105/measure/measure-x.mjs`, `BLOCK_WRITES=1`.
  - The timed lab run (X's slow profile) waits for a quiet PC. It was not run today, because the v1.0 release gates
    needed the CPU.
- **Built from it, one PR each, through orchestration's queue after the 18:00 release cut:**
