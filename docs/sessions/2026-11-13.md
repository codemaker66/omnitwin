## Field web vitals (#309, T-685): the release lead's round at c6fecbae

The release lead's review of #309 at c6fecbae held one major finding (the PR body still described the October build) and minors on privacy, the server and the front door. This round fixes them, or answers them where the decision is Blake's. Both switches stay off; #355 is stacked on #309.

### Decisions

- **A report's page is one of a list, not a shape.** `WEB_VITAL_PAGES` in `@omnitwin/types` holds every production route's pattern and `/*`; the browser sends nothing else and the API's schema accepts nothing else. `route-inventory.test.ts` holds the list equal to `router.tsx`, so a new route fails that test until the list has it. The database keeps a shape check only, which a short code spelled in letters (about 1 plan code in 6) would pass.
- **The sample rate is a decimal below 1.** Anything else, `1` included, is off: the privacy page says the browser "may" measure a page load.
- **No measurement code in a build without the rate.** The entry's condition is a build-time constant; Vercel production does not set the rate. The web `.env.example` now leaves it commented out, since any value, even `0`, keeps the code in the entry.
- **Optional chunks never reload the page.** While `loadOptional` (`route-error-boundary.tsx`) loads the reporter or its library, a script's preload failure takes no reload in the stale-chunk listener: it falls to its own import, which for a route is the route boundary (it reloads on that error) and for the reporter is its catch. A stylesheet that will not preload still reloads, since the route boundary does not know that error.
- **The daily ceiling is each process's count.** A restart or a second replica starts its own; the docs say so. A report that fails to store gives back its place, and only on the day it took it (`admit` returns the day). Reading the count from the database (so it holds across restarts) was not built.
- **The report's window** starts at a UTC midnight, counted in hours (`webVitalsWindowStart`): an interval of days follows the session's time zone and would move an hour across a change of clocks.
- **Cleanup passes are independent.** Each runs even when an earlier one fails; the job then fails with the failure, or an `AggregateError`.
- **A row keeps the UTC day** whatever the session's time zone; its index beside the primary key is on that day, and the report's window counts whole UTC days in hours, so a change of clocks cannot move it.
- **`buildServer(env, { logStream })`**: tests can read the production logger's lines; nothing else changes.
- **`WEB_VITALS_COLLECTION` is not in the API's env schema**, as `ENQUIRY_FUNNEL_BROWSER_SIGNALS` is not: a strict enum there would stop the API starting on a mistyped value, and anything but `on` is off.
- **Shuffled hourly batches** (Blake, 13 Nov, by the question form: "Shuffled hourly batches (Recommended)"). Rows written as reports arrive could be paired with the host's request log by row order, `xmin` and restore history. The route now holds reports in memory, with nothing about who sent them, and writes them hourly (`createWebVitalsBatch`): a group only once it holds ten, every row in random order, in one transaction. A group was one page, one device class, one arrival day and one set of vitals (round 4 made it one vital; below): a share page's own API call is logged with its token seconds before the report, the log's user agent tells phones from desktops, each row keeps its day, and CLS comes only from Chromium, so a lone page, phone, day or Android among iPhones would otherwise be singled out (the release lead's point and the batching self-review's major finding). A group of today under ten waits; one of an earlier day, or any at shutdown, is dropped. Each write is bounded to 15 seconds. Limits, in the doc: ten reports, not ten people (repeat loads or deliberate decoys fill a group), and a page opened fewer than ten times a day per device and browser is never measured. (Round 4 changed these: ten samples of one vital, within one process's life in a UTC day; below.)
- **#355's wording** (Blake, 13 Nov: "Apply all three (Recommended)"): the GPC/DNT sentence, a lawful basis (Article 6(1)(f)) with "no third-party analytics product", and the stored rating and day named. These are for #355's round. The answers reached this session by relay after the account switch closed its question; the first was checked in the app's own answer record, and the search for the second timed out.

## #309 round 4: the release lead's review of 923b3ed6

Not passed: one blocker (B1), one major (S4) and five minors; round 2's fixes and the bundle held. Mutation checks at 923b3ed6: 15 of 15 batch rules caught.

### Decisions

- **B1: every value on its vital's step**, in the browser before it is sent and in the API before it is held (`WEB_VITAL_STEPS` in `@omnitwin/types`: 10 ms; CLS in hundredths after the second review, as at a thousandth a score could name a screen an in-app browser's user agent names), rated again from the stepped value with web-vitals' own bounds. A value's precision is its browser's clock (Chromium a tenth of a millisecond, WebKit and Gecko a millisecond), so a fractional TTFB among whole ones named the one Chromium report of a batch. 10 ms, not 1 ms: fingerprint-resisting Firefox and Tor Browser clock to 1/60 s since Firefox 103 (Mozilla bug 1692609), whose values on a 10 ms step land on residues most ordinary values share. Only a 100 ms clock, set by hand or outdated, stays apart, and the doc says so.
- **B4: groups are one vital of one page, device class and day**, not a report's whole set of vitals. A row carries nothing joining it to its report's other vitals, so its anonymity set is its group's rows in its batch; CLS still needs ten CLS samples. This ends the behaviour bias the release lead found (LCP and TTFB split by whether the visitor tapped or moved on) and lowers the threshold to ten sampled loads measuring one vital, within one process's life in one UTC day. A report keeps its place under the daily ceiling once one of its samples is written; it gives the place back only when none was and none still can be.
- **F1, B2, M3: a write is given up on only when its transaction settles.** Places come back only when the database rolls the batch back. A flush that stops waiting (15 s) says the write may still be stored and is never retried; writes never overlap, and the closing write waits for a stuck one only within its own 15 seconds.
- **M1: the drain window is explicit at 30 s since #420** (orchestration's own one-line change to `railway.json`, not #309's), covering the API's 25-second close. Orchestration's read-only log check found the graceful close ran before #420 too ("drain complete — exiting"), so Railway's unstated default was not an instant kill. A drain that long is not yet observed under load. Railway marks config-as-code deprecated, working for legacy services until 2026-12-01: raised separately, as it covers the API's whole deploy config.
- **M2: the cleanup's fatal line prints names and SQLSTATEs only**, with #247's `describeFailure` copied verbatim, so that conflict resolves to either side.
- **S4:** `web-vitals-tracing.test.ts` runs the real SDK (`initSentry`), route and server against a loopback ingest, as `sentry-capture-path.test.ts` does: the route is traced and named, and only the route beside it is sent.
- **The release lead's conditions on the plan**, each with a test: the shuffle spans the whole batch across its groups (one Fisher-Yates over all forty rows of a seeded batch, which keeps neither its groups nor any report's four rows together), and under crypto's draw four given rows of forty land side by side about as rarely as chance says. "Never adjacent" is not built, on purpose: under a uniform shuffle a report's rows sit side by side only by chance and say nothing, while forbidding it would mark side-by-side rows as two reports' (the second review's point); the table holds only the named columns, and its id is a random UUID, not a sequence; and a whole server stopped with a write stuck closes within the batch's 15-second bound, dropping what it holds, inside the API's 25-second stop (the test's stuck write holds a pool of its own; one on the server's own pool holds that pool's close until the 25-second stop ends the process, exit 1). The doc names the remaining weak link: which values go together (an LCP is never below its TTFB) within a page, device class and day.
- **Self-reviews of round 4** (read-only, four lenses, each finding put to two or three skeptics): 19 findings held at b0e4a1a2 and 21 at deeb5cb6, and a third, of the fixes at 429aee1b, held 17, none above minor. Between them they found:
  - **The request's size.** Railway's HTTP log records each request's bytes (`rxBytes`; the installed Railway CLI's own log fields), and a report's length followed its values' digits and ratings, so a row could still be paired with its request by size: B1's outcome by another road. Every report is now padded to 512 bytes (`WEB_VITALS_REPORT_BYTES`), and the API refuses any other length.
  - **Restored and prerendered loads** report a TTFB of 0 and an LCP of a frame or two, values few ordinary loads have, from pages whose requests set them apart in the host's log; they are no longer measured, nor are pages the browser restored after a discard. The third review also asked that the residuals be named honestly: a cache-served TTFB near 0, and a CLS that still splits screens near a step's edge.
  - **`idle_in_transaction_session_timeout` ended the session**, and a checked-out client's error has no listener, so firing it would have ended the API process: removed.
  - **A write that never settles** no longer stops the day's housekeeping: an hourly flush waits for it within its bound, then writes nothing but drops an earlier day's groups. A closing flush drops rather than start a write in the last tenth of its bound. A stuck write on the server's own pool still holds the pool's close until the API's 25-second stop; the doc says so rather than claiming otherwise.
  - Wording: the guarantee is stated with its conditions and residuals everywhere it appears; CLS's step bounds its precision, not the screen's geometry. Tests: the rating bounds are checked against web-vitals' own exports; bounds under which a write must succeed are 500 ms; narrow pools are always ended.
- **A fourth read** (of the third review's fixes at 013c3713; one reader, read-only) held no blocker or major. Its minor finding: the closing floor's test reached the floor only on a fast machine, since on real time a slow commit ran the close to its whole bound and the test accepted that message too. The close's bound is now measured on a monotonic clock (`performance.now`, injectable as `monotonicNow`), which a change of the wall clock cannot stretch or cut; the floor's test sets how much of the bound is left and accepts only the floor's message, and a new test moves the wall clock an hour on during a close and sees it write. Its nits fixed: the longest number the schema takes is written in 24 characters (a largest report of 394 bytes, under 400), the memory bound reads the same in the doc and the code, and an unmeasured "about half as many" is gone. Two stay as they are, said here: an hourly flush already waiting when the close begins may start a write that the close then waits on within its bound (the pool's close is still ended by the API's 25-second stop), and the one-bound test allows 1.35 bounds of real time for a slow runner.

**Order and limits.**

1. L0 first, because every other lane cites its rows.
2. Then at most three lanes at once: L1, L2 and L4 first. L3 starts when one of them is waiting on Blake. L5 runs
   when a slot is free, and before piece C is designed.
3. Designs do not collide; builds do. Only one piece that changes the database lands at a time, and the others
   catch up after it. A lane changes its own services, routes and screens. It touches the shared schema file and
   the migration journal only inside its own merge slot, and a migration's number is fixed at merge.
4. Every pull request: its tested head goes to the merge queue and to the release lead's review; nothing is
   pushed after the head is sent; no lane merges its own work.
5. A piece is finished when its "done when" in the design has been watched on real work, not when it merges.
6. Each fortnight the lead reports to Blake how many wave-1 jobs became live.

**What every piece's design contains.** Intent and why; what exists today, read from origin/master with file and
line; the approaches considered and the one chosen; the change (tables, routes, screens) and what it leaves
alone; the rule in the database and the check that proves it; tests first, including the failure paths, tenancy
and concurrent writes; the migration, its backfill and its rollback; what only Blake decides; and the "done when"
from the design, unchanged. In plain words.

**Design approvals never proceed by default.** No lane writes product code before Blake has approved its design.
