## A client's question reaches the team as written (T-635 X1)

A client's page has a box for asking the venue team a question. The claim guard, which keeps the venue from
promising what the platform cannot back ("guaranteed accessible", "fire approved", "certified safe",
"legally compliant" and four more), also ran on the client's own words. A client who asked "Is the Grand Hall
guaranteed accessible?" was answered 400, and the page said the question had not reached the team.
Reproduced on isolated PostgreSQL before the fix: the question, a request for changes and a note with an
acceptance were each refused with "Unsupported claim phrase".

Now:
- A question, a request for changes and a note with an acceptance are checked for length only
  (`CreateProposalCommentSchema`, 1 to 4,000 characters). Blake decided for questions. The other two are the
  client's own words as well, so the same rule is extended to them. The page's Accept sends no note; only the
  API takes one.
- A question or a request for changes reaches the staff thread and the client's own page as written. The
  team's notice quotes it, up to 700 characters. A note with an acceptance is kept and never shown on the
  page.
- The venue's replies keep the guard, through a schema of their own (`VenueReplyBodySchema`); the desk's
  composer and reply box keep theirs.
- The schema for a stored comment holds either, so it no longer calls a client's words invalid.

Nothing else refused a client's words: the notices, the change feed, the client page's read and the staff
thread read the body as plain text, and a guest's enquiry was never guarded.

Tests:
- Isolated PostgreSQL: the question reaches the team's notice, the staff thread and the client's page as
  written; a request for changes and a note with an acceptance are kept as written; the venue's reply is
  still refused.
- The types file: the client's words pass, blank or over-long ones do not, and the venue's reply is guarded.
- The route file on a mock database: both client routes pass validation, and the venue's reply is refused.

The final check at max effort said ship. Its full API run on isolated PostgreSQL passed, and putting the guard
back on the client's words, or taking it off the venue's reply, fails the tests.

It is live: CI 36553665230 and Deploy 36555422001 passed on `8d410f01`, and receipt 36555576682 found the API
running it, with the route checks and the production browser pass.

Left open:
- **Who wrote a comment is only inferred.** It comes from whether the comment arrived through a link
  (`share_token_id`), and that reference is set to null if the link is deleted (`ON DELETE SET NULL`,
  migration 0034). Nothing deletes links today; they are revoked. If one were deleted, its client's words
  would show as the venue team's, which now includes phrases the venue may not use. Recording the author
  explicitly, or refusing the delete, needs a migration and is its own task.
- **The venue cannot quote or deny a guarded phrase.** The guard matches a phrase anywhere, so even "We
  cannot say it is certified safe." is refused. Staff will meet this more often now that such questions
  reach them. The desk says why and keeps what was typed. How the venue should answer them belongs with B4,
  which caveats are legally required.

## Staff may leave the client's layout out (T-635 A10)

Blake took A10's default. A proposal carries the client's own layout from their enquiry, drawn as it stands when
a version is saved. Staff may now leave it out. Layouts the venue draws itself come later.

On the desk, under the layout a proposal carries:
- While the proposal is in hand, "Leave their layout out" is offered when it carries the client's own layout.
  Versions saved after that carry none, and the composer's check of the next version is made again.
- Once the layout is left out, "Include their Grand Hall layout" is offered. It names the layout, and the server
  takes it only while it is still the one on their enquiry. If it was removed meanwhile, the change is refused
  and the panel shows the proposal as it is. "Include", not "put back": the layout may never have been on the
  proposal.
- Only a change that can be undone is offered: not for another layout, not for a removed one, and nothing once
  the proposal is with the client, whose version keeps what it was sent.
- The button waits while it works and keeps the keyboard's focus, and the panel says what changed.
- A line under it says when the saved version, the one Send shares, still shows otherwise: "Version 1, the one
  Send shares, still shows their layout. Save version 2 to send it without." It follows the composer's check, so
  over a layout with nothing placed, where the client would see no difference, it says nothing.

The client's page now closes with "Numbers and layout are planning estimates; the events team confirms them.
Nothing here is a safety, occupancy or compliance determination." The second sentence stays until B4 decides
which caveats are legally required.

A fault found on the way: a change to a proposal's links or title (`PATCH /proposals/:id`) checked that the
proposal was in hand and then wrote without checking again. A colleague's send landing in between let the change
reach a proposal already with the client. Now it writes only from the status it checked; otherwise it answers
that the proposal changed (409), and the desk says so and shows where it stands. This was reproduced on isolated
PostgreSQL by holding the row while the send commits, and the test fails without the fix.

The final check at max effort found the server side correct and the send race closed. It asked for these
before the push, all done (`39d6e2d0`):
- Focus. The button was disabled while it worked, so a keyboard user's focus fell to the page and the desk's
  keys stopped. It is now marked unavailable instead, and keeps focus. If it goes, focus moves to what is said in
  its place.
- What Send shares. After leaving the layout out, the panel said None while Send still shared the saved version
  with the drawing. The line above now says so.
- A button that could never work. A proposal whose stored links disagree with its deal (possible through the API,
  or in older rows) was offered a change the server always refuses. The desk now offers the change only while the
  links agree.
- A stale screen. A platform admin, who may change a proposal in any status, could change one already sent from a
  desk that still showed it in hand. The desk now sends the status it showed, and the change is refused if the
  proposal has moved.
- A lost answer. A change whose answer never came back was said to have changed nothing, though it may have. Any
  failure now reads the proposal again, and one without a clear refusal says "The change could not be confirmed.
  The layout shown is as last read."
- The answer shows at once, and the ledger's row says when the proposal changed.
- An older version, saved before versions kept the event's details, reads them as they are now, and so named the
  room of the proposal's current layout. It now names the room of the layout it carried, so leaving the layout
  out changes nothing on a page the client already has.

A second check at max effort of those fixes said ship. Its lesser points were taken too (`3d8956d1`): the line
under the control follows the composer's check, a lost answer says only what is known, focus is kept whatever a
browser does with focus as the control goes, and the label says "Include".

Left as it is: an older version that carried no layout still names the room of the proposal's current layout, so
including the layout can name a room on that version's page. Making it name none would change what older client
pages show today, for versions whose saved layout may not be recorded.

Tests:

  It names nothing for a removed layout, a layout in a removed room, another venue's layout, room or enquiry, or
  links that disagree. It covers the send race, a stale screen (a platform admin's too), including a removed

## Managers keep the inventory with the administrators (T-635)

Blake decided that a venue's managers, as well as its administrators, change its stock, approve or revoke its
equipment reservations, and prepare and approve its internal requests. Each decision records who made it and
their role.

Before, the navigation offered Inventory to managers, but the screen said "Venue administrator access required"
and the server refused them. One rule (`canAdjustVenueInventory`) allowed administrators only, and every stock
receipt recorded the role "admin".

Now:
- One rule (`INVENTORY_ADJUSTER_ROLES`) admits a venue's administrators and managers. It does not admit anyone
  from another venue, anyone with no venue, or anyone on a platform role alone. It gates stock corrections, the
  decisions on reservations and requests, and the reads those decisions need.
- Each stock receipt records the role it was made in, and so does each reservation approval or revocation. A
  revocation records whoever revoked it, not the approver. An internal request records who prepared it and who
  approved it, each with their role.
- Records made before today: stock receipts already say "admin". Reservation decisions and requests carry no
  role and read as an administrator's, since only administrators could decide then. The records are JSON, so
  nothing needed a migration.
- The workspace opens for managers. Receipts, reservations and requests say "Venue manager" or "Venue
  administrator", and their audit identifiers name the role. Other roles are not offered Inventory, and its
  address shows the dashboard's "Role restricted" screen.
- The stock import script records the importing account's own role, read from the database. It refuses anyone
  who cannot keep that venue's stock before anything is written. It used to write "admin" for any account.
- The approval screen said "the administrator confirms setup through return before approval". It now says the
  person approving confirms it.

The final check at max effort found the change correct, and ran every path a manager takes against real
PostgreSQL. But no test pinned what each decision records: five partial reverts passed every suite. The records
are now built by small functions tested on their own (`decidedRelease`, `preparedRemedy`, `approvedRemedy`).

A second check at max effort found that claim too broad in `ae5e9128`'s message: the five were caught inside the
new functions, but the same reverts made where the transactions call them still passed everything. Closed now:
- In CI, a guard holds that every reservation and request record is built through those functions, and a first
  count through the stock service, on a stub database, returns a manager's receipt as a manager's.
- On real PostgreSQL, a new suite checks the roles stored: a manager approves a reservation an administrator
  revokes, a manager revokes an approval from before roles were kept, a manager prepares a request an
  administrator approves, a manager makes a first count an administrator corrects, and the import reads the
  account's role.
- The same five reverts at the call sites, and the import pinning "admin" again, each fail a CI test now.

The last check at max effort said ship. Its remaining point is a limit, recorded here: CI pins how each record is
built, not what is stored or who the actor is before the builders see them. A change that stored "admin" after
the fact, or mapped a manager to an administrator in a route, would pass CI; the managers' suite on PostgreSQL
catches each, and CI does not run it.

Also from the first check:
- the import script's fixed role, fixed as above;
- the web's own list of who keeps inventory, which is now held equal to the server's by a test;
- this section's first draft, which said "internal requests" could be revoked, that other roles saw a refusal
  line, that older records carry no role, and that the PostgreSQL suites cannot run here.

Tests:
- Types: the rule, and the roles on receipts (a manager's first count included), reservations and requests,
  with older records still read.
- API: every stock and decision gate for a manager, for another venue's manager, and for the roles refused; what
  each decision records; the import's account.
- Web: the workspace for a manager, the role on each record and in its audit identifiers, and the two lists of
  roles agreeing.
- The check's five reverts, inside the functions and where they are called, the import's role and the role lists

After the release, anyone with Inventory open should reload it. A tab opened before would refuse the new fields

Roll forward, never back: once a decision is recorded with a role, or a manager records a count, the code before
this release cannot read it. Its decision records allow no unknown field, and its stock receipts allow only
"admin". The venue's assessment, decisions, requests, and the history and replay of anything a manager counted
would fail until the release is back.
