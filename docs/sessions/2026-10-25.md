- Root cause: drizzle 0.45 drops the table name from columns written straight into a `sql` select field when the
  select has no joins (`pg-core/dialect.js` `buildSelection`, `isSingleTable`), so `${referenceLoadouts.id}`
  inside `(SELECT … FROM reference_photos rp JOIN files f …)` reached PostgreSQL as a bare `"id"`, which both inner
  tables have. Sentry's captured SQL shows `WHERE rp.loadout_id = "id"`.
- The same rewrite made four counts silently wrong on production: loadout photo counts, a client's layouts and
  enquiries in client search (always 0), a guest lead's enquiries (counted by `enquiries.email`), and pieces per
  layout on a client profile (always 0). All five are now drizzle builders (`db.$count`, an embedded select).
- A new PostgreSQL suite on a migrated disposable database reproduced all five failures and passes after the fix;
  CI creates its database. The trap: `.claude/gotchas/drizzle-single-table-sql-columns.md`.

  dependencies (zod < 4.6.6 via `@modelcontextprotocol/*` 2.3.1; happy-dom ≤ 21.0.3 via vitest 4.1.12); every PR

## T-672 L3c: graphics-reset recovery for the planner, the walk and the tour

Lane L3c of plan 19 (started by Session orchestration, lead "Project status assessment"). File ownership agreed
with the planner lane before any code: NativeCanvas, the renderer lifecycle and recovery, PlannerCanvasBoundary and
the tour's loss path are L3c's; CameraRig, SelectionSystem, PlacementGhost, finger drag and the card dock are not.

The gap, measured in r186's source rather than taken from the brief: master already turned `onDeviceLost` into the
stopped card, but only with a manual retry that remounted the canvas (the camera went back to its opening pose and
the capture streamed again). A WebGPU device destroyed with reason `"destroyed"` froze silently, because
`WebGPUBackend` ignores that reason. WebGL2 had no restore path. The tour (classic `WebGLRenderer`) restored its GL
state in place but never asked its demand loop for a frame and said nothing.

What changed (branch `claude/l3c-graphics-reset-f892ce`):
- `NativeCanvas` puts a fresh renderer on the same canvas and hands it to R3F's store, keeping the React tree,
  scene graph, camera, walk, selection and decoded splats. Policy in `lib/native-renderer-recovery.ts`: waits for a
  hidden page, a WebGL canvas waits for `webglcontextrestored` (else a new canvas), 0/1/3 s backoff, 15 s attempt
  timeout, three losses a minute stop. "Restoring the 3D view" through `ActivityStatus`; `surface="walk"` copy.
- Found only in a real browser, and fixed: the splat host refused the replacement renderer (now
  `NativeSplatScene.attach()` hands over its sources), and the lost WebGL renderer's leftover dispose listeners
  produced 128 Chrome INVALID_OPERATION warnings (now it is disposed at the loss, with r186's trailing
  `loseContext()` skipped).
- The tour: `twin/TwinContextLossWatch.tsx`, same policy, four lines in TwinViewer.
- `?graphicsReset=<s>[:never]`, a once-per-view drill for real phones.

Evidence: 45 new test cases (2 replaced); `scripts/graphics-reset.mjs` in Chromium on the RTX 4090 restored every
surface and loss kind (the swap ~150 ms; drawn again 0.9–2.4 s after a WebGPU loss, 4.3–7.8 s via a new canvas, timed on the page clock) with state preserved and frame
intervals back to baseline: [report](../reports/graphics-reset-recovery-2026-10-25.md). Device day:
[script](../plan/device-day-2026-10-28-graphics-reset.md). Named to the planner: `hall-detail.ts` re-keying on the
renderer (exact lines sent), and an observed "0 of 12 chunks" pill with the capture fully drawn.

Review round: an independent TypeScript review (Opus, xhigh) found two HIGH defects in the swap path and both were
fixed in `19d94f00`. First, a replacement lost or failing while it started went to "couldn't start". Second, the
lost renderer's effect cleanups resized the shared canvas, which stopped a 1x display's room walk on a WebGPU
validation error; this was reproduced in Chromium first. The review also found a hidden-page remount, a drill test
passing for the wrong reason and a false PMREM claim of mine, all fixed. Re-timing on the page's own clock showed the
cover lifted before the new device's first frame (the swap is ~150 ms; the first frame compiles for 0.8–4 s). It now
