# 26 November 2026

## The Grand Assembly's Escape case: a race in the hold, fixed (T-742, #489)

- The case "Escape snaps it to the true state at once" failed master CI once on 20 November (91d55c4c): the Skip was
  not found within 60 s. The cause was a race in the product, not a slow load. `floor/assembly/recall.ts` holds a
  saved layout's room empty until the Grand Assembly takes it over and lets it go 8 s after nothing it needs is on its
  way. The planner said nothing was on its way once the room was known and the Assembly's code had run, but the
  Assembly mounts only once the 3D view has built the hall, and that first build holds the page's main thread for
  seconds. On a slow runner the 8 s ran out first: the request was dropped, the layout shown as placed, and the show
  (and its Skip) never came. A slow phone would have lost the Assembly the same way.
- Evidence. The job logs of 261 CI attempts (12 to 26 November) put the whole case at p50 14.5 s and p99 22.2 s; its
  one failure ran the full 60 s, so a longer wait would not have helped, and in that job the cases either side of it
  were the slowest of the sample. A step-by-step log of each opening, now attached to every case, showed one 5.5 s
  long task right after the Assembly's code ran on a desktop, and 5 to 7 s from code to stage on CI's runner, against
  the 8 s limit. Holding the page for 12 s just after the Assembly's code runs fails the base every time on CI's runner
  (0/3, the master failure's own signature) and passes the fix (3/3).
- The fix: the hold now counts a stage the Assembly is not yet on (`onStage`) as on its way, up to its 45 s cap, and a
  3D view that could not start is no stage. New tests in `recall.test.tsx` and `PlannerScene.test.tsx` fail on the
  base and pass on the fix. With no retries on CI's runner the fix passed the three cases 96/96 and the Escape case
  100/100. An independent review found no blocking problem; its points on the opening log were taken.
- Seen in passing, not addressed: one probe lane's `chrome-headless-shell` crashed at launch (SIGSEGV in libdbus)
  before any test code ran.

## The escalation sweep keeps its own async context (T-764)

- The lead came from #437's re-review, which found its job worker running each pass in the async context of the
  request that poked it. The escalation scheduler had the same shape: a request raised, handed over or reopened,
  and a conversation command, call `poke()` from inside the request; `poke()` started the plan there, the plan
  armed its `setTimeout` there, and every pass and every later plan inherited that request's context until the
  next poke replaced it with the next poker's.
- Proved before any change, with the SDK started as the API starts it
  (`packages/api/src/__tests__/escalation-scheduler-context.test.ts`: `initSentry` against a loopback stand-in
  ingest, a real request over http, a scheduler on its own `setTimeout`). On master the plan, the pass and the
  plan after it held the poking request's Sentry isolation scope (its URL and headers) and its active span, on
  the request's own trace; an error captured in the pass was sent as `POST /requests/:id/raise`, on that trace,
  with the request's URL, method and every header the scrubbers keep. A plain `AsyncLocalStorage` store set
  around the poke leaked the same way.
- In production the pass captures nothing itself. What the leak reached there is what the SDK records on its
  own during a pass: an error it captures by itself (an unhandled rejection), breadcrumbs, and the spans of the
  pass's outgoing calls, which joined the poker's trace.
- The cure, first half: the scheduler takes `AsyncLocalStorage.snapshot()` when it is built (at start-up, in
  diary-live) and enters it at every wake (`start()`, `poke()`, the timer), as #437's worker does. Chosen over a
  Sentry-only scope, which would cover one store and not the next, and over a context-free timer alone, which
  would leave the plan's database reads in the request's context.
- The release lead's review asked what the snapshot leaves: outside a request all work shares the start-up scope.
  Measured with the real SDK on the first head (`5d242b07`): start-up's error and both passes' errors carried one
  trace id, the start-up scope's for the life of the process, and the second pass's error carried the first
  pass's outgoing-call breadcrumb (a stand-in push endpoint's URL). The first head's own description, that a
  pass's error had a trace of its own, was wrong.
- The cure, second half: each wake also runs in a Sentry scope and a trace of its own (`inOwnScope` in
  `observability/sentry.ts`: a fork of the isolation scope with its breadcrumbs cleared, then a new trace), as the
  SDK gives each request. The helper runs the work as it is while `SENTRY_DSN` is unset, so the scheduler still
  never imports the SDK at runtime. The admin Sentry check's test now mocks only the two functions it stands in
  for and keeps the module's other exports real.
- Tests: the real-SDK test (4 cases, two pokes; the first pass calls a stand-in push service) and two unit cases (a
  poke and a start from inside a request: the plan, the timer it arms, the pass and the announcement see no
  store). Each was watched failing on the scheduler before its half of the cure: the request cases on master's,
  the per-pass case on the first head's. After the cure, every pass's error and start-up's are on three different
  traces, and the second pass's error carries none of the first pass's breadcrumbs while the first keeps its own.
  The existing stop and start, poke-during-run and newest-plan-wins cases pass unchanged.
- The release lead accepted the design and asked for four more checks, now tests:
  - what a pass sets on its scope (a tag, a user, a context) stays on its own errors and never reaches the next
    pass's, while the client's environment is on every event (failing at `5d242b07`);
  - a request handled after a pass carries none of that pass's breadcrumbs. Each request's scope is cloned from
    start-up's when it arrives, so at `5d242b07` a planner request's server error, captured by the API's own 5xx
    hook, listed the earlier pass's provider call as if the request had made it (failing at `5d242b07`);
  - an error captured in a pass is on the trace the pass's own calls carry;
  - a pass that throws is still caught inside its wake, announces nothing and plans again;
  - with Sentry off, a whole wake runs without the SDK ever loading. A `vi.mock` tripwire on `@sentry/node` proves
    it, and a runtime import added to the scheduler trips it.
- A failed pass is logged ("request escalation sweep failed"), not sent to Sentry: nothing in the sweep captures
  one today. That is unchanged here.
- The test's own client call runs in an isolation scope of its own. The SDK records this process's outgoing calls
  as breadcrumbs, and the test's fetch would otherwise sit on the start-up scope the sweep now uses; a browser's
  call is made in another process.
- Sweep of every timer, interval, microtask and fire-and-forget promise in `packages/api/src`: no other instance.
  The timers armed at plugin registration (the web-vitals key rotation and batch flush, the live-layout and diary
  heartbeats) are start-up's; the web-vitals batch only buffers inside a request and is written by its interval.
  Four single-flight fills (the verified-bytes cache, the Clerk email lookup, the public discovery cache, the sky
  forecast) share one bounded flight with the request that started it, and each joiner awaits it, and reports any
  error, in its own context: not this fault. Request-owned late work (the emails, pushes and event-bus subscribers
  a route starts) outlives its reply in that request's context by design: it is bounded, belongs to that request,
  and is not this fault either. The Foundry provider command executor is worker-shaped and has no caller outside
  tests yet; whoever wires it should start it at boot.
- Deploy and live check follow the merge.
