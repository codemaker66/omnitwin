# 26 November 2026

## The Grand Assembly's Escape case: a race in the hold, fixed (T-742, #489)

- The case "Escape snaps it to the true state at once" failed master CI once on 20 November (91d55c4c): the Skip was
  not found within 60 s. The cause was a race in the product, not a slow load. `floor/assembly/recall.ts` holds a
  saved layout's room empty until the Grand Assembly takes it over and lets it go 8 s after nothing it needs is on its
  way. The planner said nothing was on its way once the room was known and the Assembly's code had run, but the
  Assembly mounts only once the 3D view has built the hall, and that first build holds the page's main thread for
  seconds. On a slow runner the 8 s ran out first: the request was dropped, the layout shown as placed, and the show
  (and its Skip) never came. A slow phone would have lost the Assembly the same way.
- Evidence. The job logs of 261 CI attempts (12 to 26 November) put the whole case at p50 14.5 s and p99 22.2 s; its
  one failure ran the full 60 s, so a longer wait would not have helped, and in that job the cases either side of it
  were the slowest of the sample. A step-by-step log of each opening, now attached to every case, showed one 5.5 s
  long task right after the Assembly's code ran on a desktop, and 5 to 7 s from code to stage on CI's runner, against
  the 8 s limit. Holding the page for 12 s just after the Assembly's code runs fails the base every time on CI's runner
  (0/3, the master failure's own signature) and passes the fix (3/3).
- The fix: the hold now counts a stage the Assembly is not yet on (`onStage`) as on its way, up to its 45 s cap, and a
  3D view that could not start is no stage. New tests in `recall.test.tsx` and `PlannerScene.test.tsx` fail on the
  base and pass on the fix. With no retries on CI's runner the fix passed the three cases 96/96 and the Escape case
  100/100. An independent review found no blocking problem; its points on the opening log were taken.
- Seen in passing, not addressed: one probe lane's `chrome-headless-shell` crashed at launch (SIGSEGV in libdbus)
  before any test code ran.

## The job list: a Sentry scope and trace for each job run (T-702, stage 1)

- The lead came from the escalation scheduler's change (T-764), where it was measured with the real SDK: running
  each pass in the async context taken at start-up keeps a request's context out, but leaves every pass on one
  shared Sentry isolation scope and one trace.
- Confirmed on the job worker before any change, with the SDK started as the API starts it against a stand-in
  ingest on the loopback (`jobs-sentry-scope-postgres.test.ts`). Three dead jobs' alerts, two from one pass and one
  from the next, carried one trace id. A dead job's alert carried the breadcrumbs that earlier jobs' handlers had
  left, in the same pass and in the next, and the next pass's own alert (a claim put back) carried them too.
- The cure: the worker takes an injected `withOwnScope` and runs each pass's own work, and each job's run, in it,
  inside the worker's own async context, so a run's timers, late callbacks and alert stay in its scope. With
  `SENTRY_DSN` set, `startJobs` passes the one `buildOwnScope` builds (`alerts.ts`): a forked isolation scope,
  cleared, on a new trace, as the SDK's http integration gives each request one. Without the DSN nothing is passed
  and the worker behaves as before. The worker itself imports nothing of Sentry. The escalation scheduler's change
  (T-764) is to carry a helper of the same behaviour in its own file, so the two changes merge in either order;
  folding the two helpers into one, once both are on master, is T-765.
- Tests: the real-SDK suite has five cases (no breadcrumb crosses between jobs in one pass or the next; both ways,
  for two jobs whose runs interleave in one pass so that each alert comes after both have left breadcrumbs; each
  job run on its own trace; each pass's own work on its own scope and trace; and a control that a handler's
  breadcrumb is on its own job's alert), and each guard was removed in turn and watched failing; with no DSN no
  scope is built. The context test of the final wave still passes.
- The worker still ships off; what an alert carries in Sentry is seen in production only once it is switched on.
