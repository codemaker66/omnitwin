### What was done

- **The build runs from a room config** (`tools/surveyed-rooms/build-room.py`): one config per room, every path the Grand Hall never used behind a named gate (the hall opens none), and one sub-step at a time (`--list`, `--only`, `--resume`), because a whole stage held the shared machine's heavy lock for 59 minutes on 13 November.
- **Walls by master's method.** Since October the Grand Hall's walls take each part from its sharpest photograph. The room build now does the same by reusing the hall's own scripts through small seams, not a second copy (the copied port of October is what went stale). Proved on real data, the whole of the hall's end wall, master's scripts against the room build: labels, the 5 mm and 2.5 mm photographs, the portraits' varnish veil and the 2 mm image, 23 files and 49 arrays, none different.
- **A deadlock in master's label step, found and fixed.** `label-views.py` runs four band threads, each calling a matrix product through BLAS, which ran four threads of its own: on this machine (numpy 2.4.2, OpenBLAS 0.3.31) it stalled or crashed in three runs of four, once holding the heavy lock for 18 hours. A stack dump put the stall in `project.depth_lookup`. BLAS is now held to one thread there, in `build.sh` as well as in the room build; the labels are identical either way (21 arrays and the report, on a region).
- **Two faults that only a second room could show**, both fixed with tests: a wall whose rendered tiles are one texel narrower than its rounded length (gate B23), and two texels of 868,824 that the renderer placed behind its own camera at floor level, which the labels' 1 mm check refused (gate B24; they are left out and recorded). After each, the hall's results were compared again and did not move.
- **The Saloon, built twice**: on 13 November by the old blend, and on 15 November by the sharp method (12 walls, 288 detail tiles of 2 mm). Its gilt boards read line by line in the second where the first doubled and smeared them. The build's own check of the stained glass against the scan found no disagreement.
- **Two more rooms measured** into room configs, each with its numbered scripts, a README and a second check by ray casting:
  - Reception Room: an L of 16 faces, 101.75 m². Production stores a 13.4 by 11.2 m rectangle of 150 m²; the venue's own plan agrees with the scan to centimetres. Its two columns are square (0.28 m); no partition track was found; the floor rises 3 to 5 cm towards the windows. **Its window widths are a lower bound** (1.62 m): drapes hide every edge.
  - Robert Adam Room: 64 faces, 164.5 m² (lower 109.0, the steps 3.1, upper 52.5, each rounded), the upper floor 0.594 m above the lower in four risers. The venue's site gives 139.4 m²; production stores only the upper part. No vaults: flat panels between flat beams.
- **The web's room-driven path** ([#431](https://github.com/codemaker66/omnitwin/pull/431)): beside the Grand Hall's code and touching none of it, a room is drawn from the `survey.json` its build publishes. An independent review found nothing blocking and ten faults, all answered. Seen: the Saloon on a dev page (every wall strip on its wall, lettering unmirrored), and, on a stacked branch not yet in a pull request, the Saloon in the planner's own scene behind `?rooms=surveyed`, with the near wall and the ceiling stepping aside by the camera's side.

## The API's Railway settings move to Railway's new format (T-722): pull request 1

### What was found

- Railway stops reading `railway.json` on 1 December 2026. Its Infrastructure as Code guide, read on 14 November:
  "Existing Config as Code files stop being read on 2026-12-01 (hard cutoff)."
- Every setting the last API deploy used came from `railway.json`: thirteen of them, recorded by Railway against
  the file. They are what make a deploy run the migration step first, start with the command that works, wait
  for `/health/ready` and drain for 30 seconds.
- Railway's own stored copy of those settings is old. Railway's read-only `railway config plan`, run on
  14 November against a hand-written file, named eight differences: no builder, one watch path instead of
  thirteen, no migration step and no timeout for it, a `pnpm` start command the built image cannot run,
  `/health` instead of `/health/ready`, no health check timeout, and no drain. If the file were simply ignored,
  the first deploy in December would most likely fail to start, or go live without its migration.
- Railway's own translator (`railway config migrate`) drops four of the thirteen settings and writes a line its
  own `plan` rejects, so the new file is written by hand.

### What Blake decided

Asked by button on 14 November 2026, about 20:22 UTC.

| Question | Blake's answer | What it means |
|---|---|---|
| Is this the design to build? | "Approve it (Recommended)" | Pull request 1 is built. The slot that touches production needs his yes again at that moment |
| Rehearse on a copy of production first, or accept the proof deploy as the test? | "No rehearsal (Recommended)" | No second environment. A failed proof deploy leaves the previous one serving |

### What this pull request adds

- `.railway/railway.ts`: the thirteen settings, the source repository, the custom domain with its port written
  out, the stored build command as it is (leaving it out would clear it), and `variables: { managed: false }`,
  so no variable is written or committed. The private-network name is left out on purpose.
- `.railway/watch-patterns.json`: today's thirteen watch paths, the same list in the same order as `railway.json`.
  It is the one list. `/.railway/**` is not added: Railway does not read that folder when it deploys.
- `.railway/package.json` and `package-lock.json`: Railway's TypeScript kit (3.17.0), pinned, outside the pnpm
  workspace: three packages, none flagged by `npm audit`. Railway's command-line tool is deliberately not pinned
  here, because pinning it brings a package with a critical advisory into a public lockfile; the plan was run
  with version 5.74.0 of the tool, installed outside the repository.
- `.github/workflows/production-receipt.yml` reads the watch list from the new file and falls back to
  `railway.json` for older commits; if neither can be read, the receipt still counts it as a change. Its summary
  now says that "current" assumes Railway's stored settings match the repository.
- A step in `.github/workflows/ci.yml` (the browser gate tooling job) fails while `railway.json` exists and its
  watch list differs from the new file's.
- [The procedure](../operations/railway-config-move.md): why, the three steps, the slot's checklist, the proof,
  and what to do if the proof deploy fails. One pointer line to it in each of the three deploy documents.

None of these is a path Railway watches, so merging the pull request makes Railway deploy nothing. Vercel still
republishes the web, unchanged, on every merge to master, as for any pull request.

Railway may still record a deployment on the merge commit, because the branch carries merges of master that
brought in watched files. The review of 16 November read GitHub's deployment records for two earlier docs-only
merges built that way (#431 and #433): each record went inactive within about a minute, with no success. Expect
the same here. A success there would be a real deploy, to be watched as usual.

### Decisions made, with reasons

- **The CI step sits in the browser gate tooling job.** It is the cheapest job that installs nothing; a failure
  there also blocks the browser release gate, so the check cannot be passed over.
- **The CI step also fails when the new list is missing or not a list of paths**, even with `railway.json` gone.
  After the deletion it is the only list, and both the receipt and Railway's plan depend on it.
- **The receipt reads `railway.json` whenever the new file cannot be read as a list.** That can only yield the list
  Railway is really using while `railway.json` exists; once it is deleted, the fallback fails and the receipt
  fails safe.

### What this entry does not claim

Nothing on Railway has changed, and `railway.json` is still the file Railway reads.

Railway's read-only plan (`railway config plan --verbose`, with Railway's command-line tool 5.74.0 and kit 3.17.0)
was run against this exact file on 15 November 2026, and again on 16 November 2026 after master was merged into
the branch. Both runs printed the same eight changes and nothing else: the builder, the watch list, the
pre-deploy command and its timeout, the start command, the health check path and its timeout, and the drain.
Railway's summary read "0 to add, 2 to change, 0 to destroy" (the eight changes fall in two groups, the service's
build and deploy settings), with variables unmanaged. The plan only reads; it changed nothing on Railway.

The branch is pull request #440. The release review of 16 November passed it with no blocker and asked for one
round of small fixes and a merge of master. It is not merged, and nothing is deployed. The receipt change has been
run only by hand against local copies: the receipt runs on GitHub only when it is dispatched, and it has not been
dispatched for this change.

## The first-open event question, #253 (planner-qol, T-686; its PRs say T-674)

The release lead's delta review of 2d2c9d26 found no blocker and no major: the three majors of 13 November stay
fixed. Six minors and four nits were held, and one head answers all of them, on master e17ef564. The merge is
57be71e2, with one conflict: the 13 November log, where #421's sections and #253's were both appended. Master's text
is kept whole, and #253's section follows it.

- **The receipt hears the welcome leave the page (Q1).** The arrival's welcome is closed in its own unmount, as React
  removes it, so its close event fires on an element already out of the document. The receipt waited for that event
  and never spoke. It now also re-checks when a dialog leaves the page's body, or any dialog's `open` changes.
- **An unsent answer never overwrites a newer one on reopening (V1).** Each unsent answer carries what the layout
  held, as far as this tab knows, when it was given.
  - Reopened, the layout keeps the unsent answer only while it still holds that.
  - If it holds the unsent answer itself, the write landed. If it holds another, someone answered elsewhere since,
    and that answer stands.
  - When this tab's own earlier answer is seen written, the newer one's record moves on to it. Without that, rapid
    picks would mistake the tab's own landed answer for someone else's.
  - A retry made while the layout is not open stays last-writer-wins, as the PATCH is everywhere. (Corrected on
    16 November, V7: every write and retry is last-writer-wins, open or not; only a reopen looks first, and it
    compares answers, not versions. V5 then: the tab's own answer whose write it never saw land is not mistaken for
    someone else's either.)
- **An unsent answer belongs to the person who gave it (V2).** It records who gave it. It is never written as anyone
  else (dropped after a change of person), a reopen by someone else does not apply it, and a 401 retries only while
  someone is still signed in. (Corrected on 16 November, V6: a reopen of the same layout still applied it, as an
  answer held for this visit; it now gives way when someone else signs in.)
- **Only the newest answer is sent (V4).** An answer overtaken while it waited its turn never reaches the network, so
  a newer answer refused for good can no longer leave an older one standing on the server.
- **A kind a later release adds reads as answered (Q7).** A stored or device answer this planner does not know counts
  as answered with no kind: never asked, the unasked chair. It is also kept when the device's record is rewritten, so
  a tab left open across a release neither asks again nor erases the newer answer. (Corrected on 16 November, V8:
  not erased from the device, but such a tab writes it to a layout as a skip when it carries it there.)
- **The tests the delta asked for (Q3, Q4, Q5).**
  - A signed-in new plan, created and claimed by the planner page, writes the answer given while it was claimed, and
    each later one.
  - A write that fails only after another layout has opened is tried again.
  - A restored empty floor over a furnished server copy is not new.
- **Words (Q6, V3).** A test name says what it proves. The latch's comments and the design say what it promises:
  never asked while open once anything has stood on the floor, and new again when the saved copy is empty as it
  opens.
