## T-635 — X1's client page: the proposal as a document, and the version the client was sent

### Why the link had to change first

The client's link served the latest version saved. After a client asks for changes the proposal stays
visible to them and versions can be saved, so a half-finished version and its prices were on the link before
anyone sent it. The page also named whoever the newest "approval_note" comment named, a kind anyone holding
the link could post. Both are untrue states on the one page a client reads.

So the release went out in three steps, each a push to master:

1. **Migration 0082, schema first** (`78843e46`, 27 September). It adds `proposals.sent_version`, checked
   1..`current_version`, and `proposals.accepted_name`, and fills both from what the rows prove. CI
   36353024136 and Deploy 36353949228 passed; receipt 36354046853 found the API running `78843e46`.
2. **Step one: the writers and 0083** (`b0c736db`). CI 36363705129 and Deploy 36364454029 passed, and Deploy
   applied 0083; receipt 36364537364 found the API running `b0c736db`. The API records `sent_version` as what
   the client's link shows, while links still show the current version as before:
   - a send records the version sent;
   - a version a platform administrator saves while the proposal is out is on its link at once;
   - every answer, whether the client's or the team's, records the version it was given on.

   It also records `accepted_name` with a link acceptance, and clears it when the team, or the older share
   code, records an acceptance with no name. Migration 0083 then settles every row to that same rule from
   history, rather than from what 0082 happened to fill:
   - a proposal still with the client gets its current version;
   - an answered one gets the version saved as the answer was given.
3. **Step two: the link shows the version sent** (`a76e2ee1`). CI 36374743854 and Deploy 36375505240 passed;
   receipt 36375600442 found the API running `a76e2ee1`. It shipped only after Deploy had applied 0083, so no
   running code ever reads a value the previous API left behind.

The split came from a max-effort review. It found that Railway serves new code before Deploy migrates. In
that gap, a single release would have bound client answers to `sent_version` values the old API had never
written.

### What changed for the client

- **The document.** The page is an ivory document with these parts:
  - the event's date, guests, occasion and room, frozen with each saved version so a later change to the
    deal never rewrites what was sent;
  - one sentence saying where it stands;
  - the room's photograph (Trades Hall's own stills only);
  - the quote on the copper plane;
  - a forest decision panel.

  It prints as ink on white, the decision as one sentence.
- **Accepting.** On a link, accepting asks the name it is given in. Every answer sends the version the
  client read, and the API refuses one on a version since replaced (409 `PROPOSAL_VERSION_CHANGED`). The
  page then reads the proposal again and keeps what was typed.
  - An answer the proposal can no longer take (it moved on, was withdrawn, or the older code retired)
    says so and keeps the words.
  - The same version pressed again is answered as "already accepted".
- **Messages.** Client messages are the client's by where they came from ("Name (client)", "The client"),
  so a typed name cannot pass for the venue team's.
- **The older six-letter share code** shows the version sent and none of the event's particulars.

### What changed for the venue team

- **Preview as the client** (`/proposal-preview/:id`, `GET /proposals/:id/preview`, commercial roles at
  the venue):
  - it shows the latest version exactly as the client's page draws it, in a tab of its own, and stamps
    nothing;
  - a band says which version the client's link shows, or that the link no longer opens;
  - a printed preview says what it is and never carries the sent version's standing.

  The editor's Share panel previews too, where it used to open the client's own link, which counted as the
  client opening it.
- **The desk.**
  - A row says "Sent 3 days ago, not opened yet", counting only opens since the latest send.
  - The link is shown to copy, not to open.
  - A new link that would send a version saved since asks "Send version 3 in a new link?" and is stamped
    as a send.

## Reading ahead where it pays, and a change feed that never guesses

Blake asked whether the next page's data could load before it is asked for. Reading everything ahead would
double the API's work for pages nobody opens. So only reads that pay were changed:

- **The Day Board** reads the day either side ahead, but only once someone shows they may step: a mouse
  over or keyboard focus on the day controls, or a step itself. A wall tablet left on today reads one day
  per Diary change, as before. A finger's tap is the step itself, so it reads the day it steps to rather than
  start reads the step would cut short. `useCalendar`, shared with the Diary, now counts a range as settled
  only once this visit's own read has landed.
- **The event-day board** reads its board and its change feed together rather than one after the other.
- **A deal's detail** reads its seven parts at once after the venue check (eight queries, seven together).
  It now keeps a long-running deal's newest hundred notes; it had read the oldest hundred.
- **An inventory reservation's event** opens inside the app rather than reloading the page.

The event-day change feed (task #97) had taken a failed read for "no changes", and one failed poll emptied
the list. A failed read now keeps the changes last read and says so in place:

- "Couldn't read the changes, so what waits for acknowledgement is not known yet" before any read has
  landed;
- "Couldn't refresh the changes since 14:15. Showing them as they were at 14:05." after one has.

Try again says it is working, joins a read already out, and says what it found. Reads land only on the
event they were for; the board shown is the latest read's, and the changes are the latest that were read.
What is said aloud changes only when something happens, and in the venue's own clock. The focus moves only
when it has fallen to the page.

Five max-effort reviews checked this work. They found, among smaller points:
- the Day Board tripling its reads on a board nobody steps;
- a tap aborting its own reads ahead;
- one event's changes shown on another's board;
- a notice re-announced every minute;
- a retry that took the focus from a field being typed in;
- a read numbering of mine that let a failed read hide changes a read had found.

All are fixed. Each rule has a test that fails when it is broken (checked by breaking it), and the
event-day and Day Board suites held across eight runs under load. In CI's Chrome 147 the notice fits at 390
and 1,280 px, never scrolls sideways, and hands the focus as described.

It is live: CI 36384724004 and Deploy 36386024537 passed on `ccad68cd`, and receipt 36386148499 found the
API running it. Checks before the push:
- API: 3,527 tests, 293 skipped; the platform gate 116 of 116.
- Web: 581 files, 7,735 tests; typecheck, lint and the build pass.
- Chrome 147: 105 of 105 cases (Day Board, event day, Mission Control, the audits, hardening and the frame
  budgets). A few frame-budget cases on untouched pages missed only while other suites loaded the
  machine, and passed run alone.

### A Change pressed as the deal appears

CI on `b9e346e0` failed on a pipeline test that passes here: pressing *Change* on the deal's next step
sometimes left the editor shut. The panel put the editor away in an effect, and React also runs that
effect once the panel first appears. On a busy runner the press landed before that first run, and the
effect then shut the editor. The *Mark won…* and *Mark lost…* questions were put away by the same effect. A
slow phone could, in principle, do the same to a quick press. The panel now puts both away while
rendering, and only when the deal's stage changes (or it becomes another deal).

Three tests cover it:
- One presses *Change* in the commit that shows the deal, before the effects have run, then types in the
  editor. It fails on the old code every time; run here, with CI's exact error.
- One keeps the editor open through a quiet re-read and puts it away once the deal moves on.
- One puts an open *Mark won…* question away when a re-read finds the deal has moved.

Each fails when its rule is broken (checked by breaking it). The file passed 18 runs, six at a time, on a
loaded machine.

Two reviews at max effort found no reason to hold the fix back. The first reported that CI's test failed
on the old code every time once a 3 ms pause was put after the test library's last timer, and passed
with the fix. It also asked for the typing step and the third test. The second checked those tests and
the wording here.

It is live: CI 36393447346 and Deploy 36394654344 passed on `e1c523a1`. Receipt 36394819389 found
Vercel's production deployment of it done and the API's build current (the change is web-only).

## A client's answer says who, which and where (T-635 X1)

When a client accepted, asked for changes or wrote on a proposal, the venue team was told "Client approved
proposal" over "Client approved the proposal.". That did not say which proposal, which version or who, and
the notice opened the Proposals list rather than the proposal. The notice now says enough to act on:
- the title: who answered (the name given on the page, or "The client"), what they did, and the
  proposal's name;
- under it: the version they answered, then their own words in quotes. The note kept when they accept
  without a message is not presented as theirs;
- *View* opens that proposal on the Proposals desk (`?view=proposals&proposal=`). A change the hallkeeper
  must see opens its event instead, for those who read events. The team's own changes to a proposal with
  an event now open the proposal too, where they opened the dashboard.

It now reaches every commercial role, the proposal's owner among them. Sales did not hear of any answer on a
proposal with an event. Those notices belong to the event, and sales does not read internal events, so the
notification list never showed them; a salesperson who owned such a proposal was never told. Sales is now
sent its own copy without the event, opening the proposal, as on a proposal with no event, and nothing is
addressed to it on the event any more. The team's own changes are not repeated to sales, as before.

A salesperson who did not own a proposal was told of the answer but could not open it. That is closed in the
next section.

The version is the one the client answered:
- a question names the version the client says they were reading, if it is no later than the one their
  link shows. Their page now sends the one it shows;
- a request for changes made on a version since replaced is refused and read again, as it already was
  while the proposal waited on the client. Before this it was kept, and told as a request about the newer
  version, once changes had been asked for on that one.

Titles, names and notes are clipped to the change feed's limits, never through the middle of a character:
emoji, flags, skin tones and families are kept whole. Where the runtime cannot tell characters, or not one
whole character fits, whole code points are kept. Before this, a client who accepted a proposal with an event, in a name of 161 to 200
characters, lost the notice: the feed keeps 160 characters for who acted. A test fails that way with the
old label. A notice that fails to be written is logged with what was lost.

Tests:
- a unit test for the wording and the limits (`client-answer-notice.test.ts`);
- real PostgreSQL (`proposal-client-page-postgres`, `proposals-client-response-postgres`,
  `proposals-announcement-isolation-postgres`):
  - the three client routes with no event;
  - acceptance and requests for changes with an event, read back through the notification list as sales,
    staff and a hallkeeper would see them. The older share-code route, which retires on 18 October, is not
    tested with an event;
  - the copy for sales refused by the database: the answer and the event's notices stand, and the log says
    only the copy was lost.

Twenty-one mutants were each caught: each link, each role's copy, each version rule, the name, the note,
the placeholder, each limit, each way of clipping, and the log. Three reviews by the deep-reviewer agent,
which runs at max effort (its definition sets it), found the sales gap, the version a question named, the
clipping edges and the log; the third checked the last of the fixes.

## The planner's room timeline waits for the venue's day

CI on `4a452b6a` failed on a planner test this change does not touch, with the clock at 03:30 UTC ("keeps an
ordinary room planner editable when frozen history loads"). The room timeline opens on its day in the
browser's time zone, and the answer names the venue's. Its day starts at 04:00. From 03:00 to 04:00 UTC in
British summer time, a browser on UTC is still on the day before while the venue has begun the next. The
timeline showed the browser's day's phases, clickable, until it moved to the venue's day one fetch later.
A click in between chose a phase from the wrong day; on a busy runner the test's click landed on cards
already replaced.

The timeline now reads as loading until the venue's day has answered. It waits only once, so one left open
past the day's change keeps its day as before. A new test at 03:30 UTC answers the browser's day and never
the venue's, and records everything added to the page: the old timeline showed the wrong day's phases and
fails; the new one shows only "Loading room timeline".

Checks: the whole web suite (581 files, 7,739 tests), typecheck and lint passed. It needs no GPU run (no
renderer path or three.js import changed).

Both are live. CI 36404729985 and Deploy 36406426181 passed on `517a0dac`. Receipt 36406649860 found:
- Vercel's production deployment of it done;
- the API running `4a452b6a`, the answer's notices, with nothing the API is built from changed since;
- `/proposals/desk` and `/notifications` refusing a request without sign-in, and the dashboard answering.

It went to master before a review at max effort, so the deep-reviewer agent reviewed it afterwards. It
found three things, fixed in `682d7052`:
- The new test read the machine's time zone. On a machine east of UTC (a UK laptop) it failed, because the
  browser's day was already the venue's. The tests about a browser in UTC now pin its zone, and the file
  passes in UTC, London and New York.
- A timeline whose date was cleared from the address, left open past the venue's 04:00, read as loading
  for good with nothing on its way. With a phase previewed, the stage was left empty and locked. The
  mark that the venue's day had been read could be cleared without the timeline rendering again, so the
  reading never ran again. Clearing it now renders again. A new test clears the date, passes the venue's
  04:00, and finds the timeline keeping its day with nothing asked; it fails on `517a0dac`.
- Older than this fix: with a linked event near the day boundary, the timeline's zone fell back to the
  browser's while each range loaded. The event's day moved between the two zones' days, asking for each in
  turn without end (17 requests in 300 ms in the test). The timeline now keeps the venue's zone once
  any answer has named it. A new test, with a browser in UTC or New York, finds one request for the
  event's day.

`517a0dac`'s title overstated one thing. The range title still names the browser's day while the first
request is on its way, before the venue's zone is known. No phase from that day is shown or can be
chosen.

`682d7052` went to master in `f01047db` after a second review at max effort (ship; live by receipt
36413988600). That review's small points followed in `9d0be153`: the deep-link date test pins its zone,
since at noon UTC a browser in Honolulu is still on the day before, and two comments now say what the code does.

## Opening a proposal or a quote: the venue's commercial roles (T-635 X1)

Opening one proposal (the proposal itself, its versions, history, comments and next moves) or one quote
used the owner-or-venue-floor rule. That rule let the wrong people in and kept the right ones out:
- a salesperson who did not make the proposal was refused, so the *View* on a client's answer, and the
  proposal's own row on the desk, failed with "The proposal could not be opened.";
- a hallkeeper could read a proposal's or a quote's prices. The recorded decision is that hallkeepers never
  see prices (goal 18 6b);
- whoever made a record kept it after their role or venue changed, against the house rule that who made
  something is not a lasting grant (no product flow changes a person's role or venue today). The lists
  kept it too: the proposal list, the Proposals desk and the quote list showed anyone outside the
  commercial roles the rows they had made, prices with them.

Opening and moving one now take the same people as every change to it: the venue's commercial roles
(staff, admin, manager, sales) and a platform admin (`canManageCommercial`). The three lists take the same
people and refuse anyone else, as the pipeline's list does, where before they showed them their own rows.
The state machine still decides which moves each role may make. No screen changes: the dashboard shows
the Proposals desk to those roles alone, the web opens single proposals from that desk and the preview
page, and the editor's Share lens moves one its user has just made as a commercial role. No screen reads
a quote list or a single quote.

Tests on the disposable databases (`proposal-permissions-postgres`, `quote-permissions-postgres`,
`proposals-desk-postgres`):
- sales, a manager, staff and an admin open a colleague's proposal (all six reads) and quote, and sales
  sends and issues them; a platform admin opens another venue's;
- a hallkeeper, a client, and staff or sales from another venue are refused every read and a move, and
  nothing changes. A hallkeeper is refused the three lists, and a planner the desk, even for a proposal
  they made;
- a maker who is now a hallkeeper is refused every read, a move and all three lists, and no answer
  carries the row.

With the old rule the sales and hallkeeper cases fail, and with a maker clause back the maker case fails.
With the maker's reading back on any list, the venue's rows shown to anyone there, or an empty page in
place of the refusal, the list cases fail (six mutants, each caught). A review by the deep-reviewer agent
(max effort) found the maker clause and the untested cases; both are fixed. It also found that two moves
of one quote at once both succeed (a quote's move is not held, as a proposal's is), which is left open
below.

A second review at max effort, of the lists' refusal, found no reason to hold it back. It asked for tests
of cases the code got right but nothing pinned, added in `52273a6c`:
- sales, a manager, staff, an admin and a platform admin find a colleague's proposal in both lists, and a
  platform admin finds another venue's quote;
- a client, a caterer, a planner and a salesperson with no venue yet are refused the lists. Staff and
  sales from another venue see their own venue's rows, not ours;
- a hallkeeper, a client, another venue's staff and a maker now a hallkeeper cannot make a share link or
  comment, and nothing is written.

It also found the same grant on the planner's timeline. An event's revenue estimate went to whoever made
the event, as well as to the commercial roles. Only staff, admins and managers make events, so it reached
only someone who had since left those roles. The estimate now takes the commercial roles alone. The
timeline's database rehearsal proves this for the maker made a hallkeeper; it was run here on a freshly
migrated database. CI does not run that suite, so a source test holds the rule on every push. Nine more
mutants were each caught.

It is live. CI 36412250895 and Deploy 36413818738 passed on `f01047db`. Receipt 36413988600 found the API
running `f01047db` itself and Vercel's deployment done; `/proposals`, `/proposals/desk`, `/quotes` and
`/calendar/layout-timeline` refuse a request without sign-in.

### Left open

- Blake's verdict on the document's look.
- A quote's move is not held against a move at the same moment, as a proposal's is: two at once both succeed
  and the later wins (read from the code, not reproduced).
- The room timeline with a linked event near the day boundary: when the event arrives before any answer has
  named the venue's zone, the event's day read in the browser's zone is shown once, and can be chosen,
  before the timeline moves to the venue's day. This is older than today's fixes and now happens once, not
  in a loop. Holding the event's day until the venue's zone is known would wait on a request for a day
  nobody asked for; marking it provisional, as the automatic day is, must not risk another stuck wait.
- An account in a commercial role with no venue yet (an invitation or an approved domain) is still offered
  the Proposals and Pipeline desks. Both say they could not be read: the Pipeline already did, and the
  Proposals desk now does too. It should be told the account has no venue yet.
- X1's remaining *Proposals* lines: a price list, templates, and linking the deal, enquiry and layout on
  creation.
- The older share code retires on 18 October. Every test that uses it now pins its own sunset; the last
  that did not would have failed four of its five cases from the 19th (run with the clock set to that day).
