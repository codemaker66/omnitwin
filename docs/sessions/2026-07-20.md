## T-538 · REST command idempotency — one ledger, both transports (Diary lane)

Blake's direction ("extend REST with commandId idempotency so both
transports share the ledger") — the T-537 reviewer's "complete fix",
chosen over the Redis backplane (which needs infra this machine can't
host and only matters at replica two).

- **Server:** booking create/update/transition accept an optional
  `Idempotency-Key` header (uuid commandId). A keyed request runs THROUGH
  `executeDiaryCommand` + `realDiaryCommandDeps` — literally the ws
  transport's function, so the ledger write inside the mutation
  transaction, the savepoint law, duplicate replay, and the replay
  venue-authorization are inherited, never re-implemented. The new pure
  `ackToHttpReply` maps acks onto the EXACT keyless reply shapes
  (`{ data }` / `{ data, resequence }` / sendDeny), with an honest 404
  for an applied replay whose booking was later deleted, and the route
  sets `Idempotency-Replay: true|false` (CORS-exposed via
  `exposedHeaders`). Venue-less actors are refused with
  400 `IDEMPOTENCY_REQUIRES_VENUE` (ws-door parity); keyless requests,
  reads, and from-enquiry are byte-identical to before.
- **Client:** `sendViaChannelOrRest` mints ONE commandId per logical
  operation; the channel attempt and `restFallback(commandId)` share it
  (`api.post/patch` gained an `idempotencyKey` option → the header). The
  T-537 refusal guard (`COMMAND_UNCONFIRMED`) retires: identity
  supersedes refusal, so a committed-but-unacked create's retry REPLAYS
  instead of duplicating. Channel tests evolved to same-id assertions —
  the invariant ("an unconfirmed create must never duplicate") is
  unchanged, its enforcement is stronger.
- **TDD:** mapper contract written first (7 red → green);
  `bookings-idempotency.test.ts` pins the boundary (header validation on
  all three surfaces, venue requirement, hallkeeper at the command gate,
  actor-venue create scoping, source pins incl. "reads and from-enquiry
  carry no idempotency surface").
