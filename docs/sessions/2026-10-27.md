## Plan 19 L5: deposits in Stripe test mode, and the contract's electronic signature (cloud session)

Blake kept L5 in the 31 October scope on 27 October, test mode only, never taking real money. This session built it
as four stacked PRs for the local orchestrator to merge and GPU-gate. None of them is merged or deployed.

- **#269, schema, gateway, webhook.** Migration 0103 adds deposit requests, their Checkout payments, contract
  versions and signatures, each pinned to the proposal's venue by composite keys. Payments are `livemode`-CHECKed
  false; contract records are immutable by trigger. The stripe-node 22.6.2 gateway is the only code holding the key.
  The API will not start with a non-`sk_test_` key unless `STRIPE_LIVE_PAYMENTS_ALLOWED=true`, which nothing sets,
  and the payment routes refuse it again. `POST /webhooks/stripe` verifies over the raw body, refuses live events,
  and applies each event once, in any order, as facts.
- **#273, deposit flow.** The venue asks for an amount or a percentage of the **accepted** quote (`sent_version`),
  and the request is checked against it again before Stripe is called. The client pays on Stripe's page. There is one
  page per request, and a withdrawn request closes its open page. Declines, settling payments, refunds and mismatches
  are said plainly. Only the configured venue offers deposits.
- **#283, contract signature.** The server prepares versions from the accepted version, the addressed client and the venue's
  terms, hashed. The client signs the exact version shown, with a typed name and a ticked statement. The record keeps
  the name, the email of record, the time, the hash, the user agent, the statement and the link prefix, with no IP
  address. A change makes a new version. The privacy page names Stripe and the signature record (dated 27 October).
- **#284, acceptance lines.** Goal 06's pain points 1, 4 and 9 pass end to end on migrated PostgreSQL. The other nine are
  pending with the slice that owns each.

An independent adversarial review (deep-reviewer, at max effort) of the three code PRs found five defects, each
reproduced and now fixed:

1. Withdrawing a request, or reopening checkout, trusted database state that lags Stripe. The fix closes pages at
   Stripe first, refuses a new request while money is held, and shows a settled withdrawn request to the client.
2. The share token was sent to Stripe in `success_url` and `cancel_url`. The fix returns through `/deposit-return`.
3. A refunded deposit blocked the proposal permanently. A full refund can now be withdrawn.
4. The client page offered a Sign form the route refused, for archived proposals. The page and the route now share
   one `signable` check.
5. Staff panels hid records when deposits were off or the client's email had gone.

Hardening from the same review:

- The reported amount and currency are judged together, in a fixed order.
- A payment reported without an amount is a mismatch.
- The client sends back the statement it showed.
- NUL characters are refused.
- Adaptive Pricing is off.

Its "sound" list covered the test-mode lock, raw-body verification, idempotency, tenancy, the accepted-version rule,
concurrency and the migration.

Decisions recorded here:

- **Checkout over the Payment Element.** No Stripe.js, no publishable key, no CSP change; Stripe handles 3-D Secure,
  wallets and receipts. As a result Vercel needs no variable.
- **The signer's email** is the email of the client the proposal was addressed to (the deal's contact, else the
  enquiry). The signed document names it. A share token carries no recipient of its own.
- **No IP address** in the signature record. The privacy page says so.
- **Partial Stripe configuration refuses startup,** as R2's does.
