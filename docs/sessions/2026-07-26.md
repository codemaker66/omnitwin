## T-539 · The Diary → planner corridor

The panel's winning proposal ("The Turn") rested on a premise that turned out
to be **false**, and checking it changed the work:

> *claimed:* `packages/api/src/routes/bookings.ts:289` hardcodes
> `eventId: null`, so the API silently discards the booking→plan link in both
> directions.

That `null` is inside the **enquiry conversion**, where a pencilled-in
enquiry deliberately has no plan yet (Canon §1 — the commitment axis and the
enquiry axis stay independent). The real cores have honoured `eventId` since
the T-537 extraction: `booking-mutations.ts` validates the event against the
booking's venue (`EVENT_VENUE_MISMATCH`) *before* writing it, on both create
(`:223`→`:245`) and update (`:310`→`:346`). The agent read the thin route
adapter and inferred a defect from it.

**The genuine gaps were:** (1) nothing tested the link — which is precisely
why reading the adapter alone makes it look broken; (2) nothing in the client
ever sent it, so a coordinator had no way to say *"this booking is the thing
I am planning."*

Shipped:

- **API pins** (`bookings-routes.test.ts`, new describe block): the venue
  check precedes the insert; an explicit `null` survives the update merge
  (`=== undefined` is load-bearing — `??` would collapse "not supplied" and
  "detach"); the conversion's `null` is deliberate; the serializer carries
  the link; a malformed `eventId` is refused at the schema boundary.
- **Client**: `api/events.ts` gains `createEvent`; `EditBookingPatch` gains
  `eventId`; the booking drawer gains a **Floor plan** section — start a plan
  (seeded from the booking's name, type and window), open it at
  `/plan?eventId=…` (exactly what `use-linked-event.ts` binds from), or
  detach it. A real anchor, not a router push: the planner is a heavy 3D
  route and a deliberate context switch, and an anchor keeps the drawer
  testable without a router.
- **Failure honesty**: if the event commits but the link fails, the booking
  is left untouched and the drawer says only what is true — pinned by a test.

Built on a fresh branch `feature/diary-plan-link` cut from current master in
its own worktree (`C:/omni-link`), because the shared tree carries 134
modified and 329 untracked files across parallel lanes — six of which master
also touches. Merging in place would have required stashing another lane's
uncommitted work.

**Not done, deliberately:** the changeover engine ("The Turn" proper) waits
until a coordinator has actually used the link; and Sightline/The Setting
stay blocked on a fitted planner-room→E57 transform, which deserves its own
T-number (all 149 twin scan nodes currently carry `roomSlug: null`).

### Adversarial review (27 agents: 4 lenses → per-finding refutation)

28 raw findings; most evaporated on contact with the code. Three that stood
were fixed in the same session — all three were **honesty** defects, which is
the class this codebase least tolerates:

1. **The copy promised something the code did not do.** `planNone` read
   "Starting one *opens the planner*…" — `startPlan` never navigates; it
   closes the drawer with a toast. Rewritten to describe what actually
   happens.
2. **`planFailed` said "the booking is unchanged" in the one case where a
   plan had just been created.** Starting a plan is two writes that cannot be
   one transaction (create the event, then link it). If the link fails the
   event is already committed — and `routes/events.ts` exposes no list and no
   delete, so an orphan is invisible litter forever. Worse, a natural retry
   minted *another* one. Fixed: the created id is held in a ref, so a retry
   FINISHES the link instead of repeating its first half, and a distinct
   message says the plan exists but is not attached yet.
   Reachable failure modes are real, not just network: `updateBookingCore`
   re-validates the MERGED hold on any patch, so an `{eventId}`-only patch on
   a hold missing a hygiene field is refused 400 — and `startPlan` bypasses
   the form validation that normally shields that seam.
3. **No role gate.** The section rendered on `mode.kind === "edit"` alone, so
   a hallkeeper (read-only) was offered a control whose every path ends in
   403. Now gated on staff/admin, matching the API.

**Known and NOT fixed — recorded rather than hidden:** the drawer renders a
booking *snapshot* captured at open (`DiaryBoardPage.tsx:95-100`) which no
refetch or live event refreshes. On a deliberately multi-coordinator board,
if A attaches a plan while B has the same booking open, B still sees "no
plan" and starting one relinks the booking, orphaning A's event. The honest
fix is to re-derive the drawer's booking from `bookingById` each render — a
change to the parent's drawer-state model, not to this slice. It predates
this commit for every other field in the drawer.

Also surfaced and worth its own task: **`POST /events` performs no venue
authorization** (`routes/events.ts:258` has `preHandler: [authenticate]` and
nothing else), while every booking write checks `canManageVenue`. That is a
pre-existing tenant-isolation gap, not introduced here.
