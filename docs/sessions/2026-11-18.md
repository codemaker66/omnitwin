## The API's Railway settings move to Railway's new format (T-722): pull request 2

- Pull request 2 is the branch `claude/railway-config-remove-json`, on top of #440's reviewed head, pushed at

  Its second, `de6e4b59`, adds two things to the procedure's slot checklist: the slot-day pre-step (merge master

### What this pull request does

- Deletes `railway.json`.
- Corrects the comments that named `railway.json` as the home of a setting: the start command in the
  `Dockerfile`, the health check path in `packages/api/src/index.ts`, the pre-deploy command in
  `packages/api/src/scripts/migrate-before-deploy.ts`, and the Deploy workflow's header. Each now names
  `.railway/railway.ts` and Railway's stored settings. Comments only: no code changes.
- Keeps `/railway.json` in `.railway/watch-patterns.json`, and changes nothing under `.railway/`. The path is
  harmless once the file is gone, and removing it would need another apply.
- Renames the CI step that compared the two watch lists and corrects its comment. Its logic is unchanged. It
  still fails if the list is missing or is not a list of paths. It compares the list with `railway.json` only if
  that file comes back, for example in a revert of this pull request, which Railway would read until 1 December.
- Makes the production receipt count a renamed file by its old name as well as its new one, so a file moved out
  of a watched path counts as a change (a follow-up from #440's review). This can only make the receipt's
  "unchanged" verdict rarer, never more common. Its fallback to `railway.json` for older commits stays.
- Corrects the sentences that named `railway.json` as the place a setting lives in the deploy documents: deploy
  ordering, the current deploy flow, the diary deploy checklist, the runbook (its migration section, its Railway
  deploy note and two of its known-flakes entries, one of which gave a start command that cannot boot the API)
  and the web vitals note. Their dates and pull request numbers are kept.
- Adds to the procedure's slot checklist: the slot-day pre-step and step 7's backstop wording (`de6e4b59`); and,
  from the release lead's early review: no Deploy workflow run approved or running during the slot; required
  checks, with the Security Audit job's known failure on master not blocking; a stop if the plan refuses the
  service over a config-file path; a stop if the apply's own deploy fails; that after any stop the hold on merges
  is released and the slot rebooked by 27 November; and that pull request 2 stays a draft until step 6 exits 0,
  then is marked ready for review and merged at once. The rest of the page, the record of the move as planned,
  is not changed.

### Why it merges only in the slot

It touches watched paths on purpose: `railway.json` itself, the `Dockerfile` and two files under
`packages/api/`. So merging it starts a deploy, the first with no `railway.json`, and that deploy is the proof.
It merges straight after the apply and after Railway's plan shows nothing left to change
([the procedure](../operations/railway-config-move.md), steps 4 to 7). Merged before the apply, it would deploy
with Railway's old stored settings.

Because it changes the `Dockerfile` and two API files, the merge should start a deploy whether or not Railway
counts a deleted file as a change. The procedure's ten-minute rule still stands.

### Decisions made, with reasons

- **The CI step stays.** With `railway.json` gone it still checks that the one watch list is a non-empty list of
  paths, which Railway's plan and the receipt both depend on. Its compare branch is kept for a revert.
- **Nothing under `.railway/` changes.** A pinned plan pins that folder. This pull request merges after the
  apply, so a change there could not break the apply, but no sentence there becomes false, so there is nothing to
  change.
