## The job list: how it works, written down (T-702, stage 1)

Documentation only: no code, test or migration changed in this entry.

### Built, on the stage 1 branch

- The `jobs` table and its claim, a worker inside each API process, repeating jobs,
  alerts, the daily check, `GET /health/worker`, four admin routes
  (`/admin/jobs/stuck`, `/retry`, `/close`, `/selftest`) and the Stuck work page.
- The note for the next engineer and for whoever reads Stuck work:
  [the job list](../engineering/the-job-list.md). It gives the seven rules a kind's
  author follows, each with its reason, and how to change a kind's data in two deploys.
- The engineering map has a row for the area and a row in its reference table. The
  operations note's bullet that said the cron owns timing was replaced; see the
  20 November log for what it says now.

### Switched off

- The worker ships off: `JOBS_WORKER` unset means off, and `JOBS_MAX_SLEEP_MINUTES`
  unset means 60.
- No email goes through the list yet. The request-escalation wake and the clean-up
  passes still run by themselves.
- Only two kinds exist: `jobs.selftest` and the list's own `jobs.daily`.

### Not yet proved

- Nothing has run in production.
- The migration is `0110_job_list.sql` (journal idx 107) and its number is fixed only
  when it merges. A renumber needs a journal `when` later than master's newest entry,
  because the migrator applies by that time and would skip an older one.
- The two-server test (`jobs-two-process-postgres.test.ts`) is a CI test. No two
  servers have shared the list in production.

### Decided

- **The lock order has five steps, not three:** bookings, then the proposal, then the
  enquiry, then the deal, then the event (the spine's design, section 5.4). The build
  plan's constraint listed three; it is corrected, and the note gives all five.
- **A handler that never answers while the server stops** is ended by its own limit
  (15 seconds at most, inside the 18-second stop allowance) and recorded as a failed
  try, not put back untouched.
- **Try again refuses a kind this server cannot read** (409 `JOB_KIND_UNREADABLE`);
  such a job can only be closed with a note. This is why a kind's data changes in two
  deploys: the reader for the old version stays until no job of it is left.
