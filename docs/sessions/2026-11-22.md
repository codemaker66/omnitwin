## The API's Railway settings now live in Railway's new format (T-722): done

`railway.json` is gone from master, and Railway deploys the API from its own
stored settings, which `.railway/railway.ts` declares. The move was done in one
slot today, five days before the date we set ourselves and nine before
Railway's cutoff. The full record, with times, is
[the outcome](../operations/railway-config-move.md#the-outcome-22-november-2026).

### What happened

- Pull request 1 (#440) had merged on 20 November. Pull request 2 (#447) was
  brought up to date with master twice today; the release lead passed it after
  each merge, the second time against its own trial merge.
- The merge coordinator held every merge to master for the slot.
- A pinned plan from a clean checkout of master showed the same eight setting
  changes as every plan since 14 November, and nothing destructive.
- Blake said yes to the apply by button. The apply ran, Railway redeployed the
  API once with its migration step, and a second plan showed nothing left to
  change.
- #447 was then marked ready and merged. The deploy that merge started is the
  first without `railway.json`. Its own record names no config file, carries
  every setting, and its log shows the migration step before the start.
- The production receipt passed on the merge commit.

### Decisions made, with reasons

- **The apply waited for pull request 2's last check.** Blake's yes came while
  one check was still running. The checklist wants every check green before the
  production step, so the apply waited about fifteen minutes and the pre-flight
  was repeated. Applying first would have risked a longer spell with the
  settings in two places if that check had failed.
- **Blake looked at Railway's dashboard himself.** The checklist's first step
  is a look for pending staged changes. Railway's tool does not show them, and
  an agent should not sign in to the dashboard, so the look became part of his
  yes.
- **The plan and the apply ran from a clean, detached checkout of master**, not
  from a working branch, so the pinned plan's folder was exactly master's.

### What this entry does not claim

- Nothing checks, from now on, that Railway's stored settings still match
  `.railway/railway.ts`. Until something does, a change made on Railway's
  dashboard shows only on the next plan.
- The small things left over are listed in the outcome. None is fixed here.

## The planner's kit, stage 1a (T-719, lane L4)

Stage 1a of the design merged in #426 is built: a guest list an event planner keeps on their own device, seats
from the list and prints. Two pages, `/plan/:code/guests` and `/plan/:code/guests/paper`, show the not-found page
until `?kit=on` has been given on that device. Web only: no API or database change, no change to sign-up or to the
planner's own chrome, and nothing links to the pages yet.

- **How it was built.** Thirteen tasks from `docs/superpowers/plans/2026-11-13-planners-kit-stage-1a.md`, each built
  test-first by one helper and reviewed by another. Then one whole-branch review (2 must-fix and 6 should-fix
  findings), one fix wave, a re-review of the fixes, and six small points closed after it.
- **It rests on Blake's approvals of 13 November**, recorded in the design: the design itself, the look, the
  done-when test, and five invited planners first, on their own devices.
- **What holds the promise that no name leaves the device:** a guard test that parses every kit source file
  (errors, logs, class names, ids, addresses, ways out, spelling services); a canary name followed through every
  function; and a browser test that records every request and every WebSocket.
- **Decided along the way, for Blake to see:**
  - The page says "None of them is sent to Venviewer." An uncaught error on a kit page is still reported by the
    app as on any other page; the kit builds no error from data, so the report carries no name.
  - The kit's two routes report no web vitals, agreed with T-685's owner. The list of pages a report may name is
    unchanged; the route inventory test holds the silent routes to the router.
  - A date that would remove the list at once is refused, in words. A print counts as a change for the 90-day rule.
  - A list written "Surname, First" is read as whole names, and the first guest is shown before anything is added.
- **Measured in a real browser.** From opening the page to the print dialog with 180 guests on 18 tables: 6 clicks
  (budget 10), 1 typed field (budget 3), one paste; 255 requests, all reads, and the one that left the app was the
  read of the plan. The version line is on every printed page of the three list sheets and on no place card, read
  from Chromium's own PDF page by page. The route audit passes for the empty list, a seated list and the paper,
  each at three sizes. The guest pages' chunks reach no 3D code.
- **Verified locally** on this branch's code over master 7bb19469: the types build, the web typecheck (src and
  e2e), lint (no errors), 19 test files of the kit and the web vitals reporter (503 tests), the web build, and 11
  repository-wide guard test files, the route inventory among them. The machine ran short of memory during the
  first pass, so lint and two guard files were run a second time on their own. The whole web suite runs in CI.
- **Not done.** Nobody has yet watched a planner use it: the agreed test with five planners has not been run.
  There is no way in from the planner's own chrome yet. Printing was measured in Chromium only. The follow-up list
  from the review is in the pull request.
