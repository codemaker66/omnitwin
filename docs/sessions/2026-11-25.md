## The job list: the fixes before merge (T-702, stage 1)

A review of the whole stage 1 branch found one critical problem, six important ones and smaller notes to fix before
merge. All are fixed on the branch. It is still not on master, and the worker still ships off.

### What changed

- **Every pass of the worker begins in its own async context.** A pass began in the context of whatever woke it, so
  a poke made inside a request lent that request's context to the passes, handlers, alerts and timers after it. Each
  pass now begins in the context the worker was built in.
- **A job that goes dead always raises its alert.** When recording a failed try passed the worker's limit, the late
  answer was dropped, and a job could go dead with no alert. Whichever answer records the try is now told, once.
- **What a late callback throws is caught**, and a pass whose own handling of a failure throws is a loop fault, with
  its alert. The worker refuses a database call limit that is not under the claim's 15-second margin.
- **Work stuck unseen has an alert of its own**, `job.list-stuck`, apart from the worker's loop fault. The daily
  check raises it, and so does a repeating kind with no next run.
- **One faulty repeating kind cannot stall the others.** A kind whose next run throws, or is not after now, is
  skipped, logged and alerted, the other kinds still get their runs, and the pass completes.
- **Stuck work's "N are waiting" counts the queued jobs that are due now**, not the daily job's next run or a try
  waiting out its retry.
- Tests that could not fail now fail without the rule they name: the self-test's bounded wait, a send that names
  another venue's enquiry, and focus after a refused Close on Stuck work. The two-server test no longer gives up on a
  child whose last message is still on its way.
- [The job list](../engineering/the-job-list.md) note gives the order for changing a kind's data: first the code that
  reads both shapes, then the code that writes the new one, and later a clean-up that drops the old. The migration's
  header says which tables it holds and for how long. The task row, the build plan and the 18 November log state the
  decisions in neutral words.

### Not yet proved

- Nothing has run in production, and the migration's number is fixed only when it merges.
- What a Sentry alert carries after the context fix can be seen only once the worker is switched on.
