# 25 November 2026

## The planner's kit, stage 1a: the review's fixes (T-719, lane L4)

The first full review of #472 did not pass it. It confirmed that no guest's name leaves the device by any path,
that the printed version numbers are right and that the browser gate's admissions were exact, and it asked for
eleven fixes in one push. Each was checked against the code first; all held. Each fix has a test that failed
before it.

- **Two tabs.** A kit page mounted again over the page state it already held read nothing from the device, so its
  next change could overwrite another tab's list or write a deleted list back. Both pages now read the device
  every time they mount and stay in their opening state until that read returns. A stored copy has an identity (a
  count of saves and its writer's time), and tabs are reconciled on "the stored copy is not the one I loaded",
  never on which clock is later. A save that finds nothing stored where it had loaded a list writes nothing. A
  print's save gives way to another tab's list, and the page says the printout was made from an older copy; the
  print is recorded on their list, so its number is not reused.
- **Decided along the way.** The browser's own Print command makes no read first: it is synchronous, and the sheet
  laid out as it returns must carry the new version number. The reads at each mount, on focus and when the page is
  seen again keep the list current before it. The release lead agreed.
- **Retention.** Lists past their removal day are also removed a little after any Venviewer page starts, from a
  lazily loaded module that opens no database where none exists. The page now says "on or after" the day, the next
  time Venviewer opens in that browser.
- **Closing a tab.** Measured in Chromium, ten runs each: a change made about 100 ms before a close was lost every
  time. The save now starts as the page is left, and the browser asks before a tab closes over a change not yet
  kept (10 of 10 inside the window, 0 of 10 once the save has finished). A close with no confirm still loses it.
- **Names and paper.** A name written "Surname, First" is filed under the surname. The list page and the table plan
  share one A to Z, so a letter is one section on both. A long name on a place card is set smaller, in three steps;
  the print checks now read every name from the PDFs and measure each card.
- **The page.** The wheel over the list reaches its last guest at 1366 by 641, 1536 by 704 and 1920 by 953 (one new
  browser case). A refused move is said in a region that is always there, and a full table offers no "Seat here".
  Guests' names are marked not to be translated.
- **The gate.** #388 merged first, so the kit's browser cases were admitted again on master's 432: sixteen cases in
  two admissions, 448 in all.
- **Closed on 26 November, before the push.** The kit's own guard caught a place card's size step being written
  from the guest's name inside an attribute; the step now comes with the card, and no attribute is built from a
  name. On the Print button's path a save that gives way no longer speaks of an older printout, since nothing has
  been printed then: the print is recorded once more on the list the page shows, and that is what is printed. And
  a delete the browser refuses is no longer shown as done: the page reads the device again, keeps the list on the
  page and says it could not be deleted.
- **An independent read of the two-tab code, before the push,** found one major fault and eight smaller ones.
  Eight are fixed, each with a test that failed first. The major one: a save over a copy another tab had printed
  wrote a lower paper version back, so the number of a sheet already out could go to a second, different sheet. The
  device now keeps the larger number, and the page takes it up. The others: a take-up puts away what the page was
  saying about the copy before; starting again from a value that could not be read takes up a list another tab has
  stored there since, where it used to erase it; a change kept over another tab's copy after the page had left that
  plan is said when the plan is next opened; a value that cannot be read is removed 90 days after it was last
  stored; the Print button stops when its read finds the list gone; the browser's own Print during the button's
  wait is recorded; and the paper page asks before the tab closes while a save is waiting.
- **Left from that read, and said in the pull request.** A save's read and its write are two steps of the store, so
  a save already in flight can undo another tab's delete made in the few milliseconds between them. Both tabs then
  say what happened. One step for both needs a small addition to the shared storage helper, in its own change.
- **Not done.** Nobody has yet watched a planner use it. The fixes made after the independent read have had no
  second one: the release lead's review of this push is that check. The follow-up list is in the pull request.

## The planner's room bounds (#411) are reverted for a capacity regression (T-760)

- #411 merged on 25 November as `732cf511`. Its live check proved its aim: the planner's own Lay out put no piece
  outside the drawn walls in the Saloon, the Reception Room or the Robert Adam Room.
- The same live check measured the banquet fills it produced: 30, 30 and 40 seats, against 40, 60 and 60 before it.
  The venue publishes 60 dinner covers for each of the three rooms (`TRADES_HALL_ROOM_CAPACITIES`). Before #411 the
  Reception Room seated 60 with every piece's centre inside its drawn walls, so the walls admit 60, and #411's stated
  limit (about 2.5 % of corner spots) does not describe a halving. The release lead ruled it a regression.
- #411 is reverted as a stopgap: its 35 code and test files return byte for byte to their state at `8ccf0d1e`
  (which already holds #388 and #389, so this is not a rollback past #388). Its six task rows stay, each noted as
  reverted. The Robert Adam Room's through-wall fill, a known defect, is live again until the re-land.
- T-760 is the fix and #411's re-land, owned by the audit lane. Its proof measures whole-room fill counts before and
  after in every shaped room.

The review of #479 named three places that still give the Reception Room's 13.4 × 11.2 m, because they read the
database's row and not the venue-truth record: the venue read for AI assistants (`get_venue`), the public read of a
venue's spaces, and a client proposal's layout summary for screen readers. They were put to Blake with three choices:
make `get_venue` leave the size out, leave all three, or change the stored room now. **He chose to leave all three for
