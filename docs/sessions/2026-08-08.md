# Session log — 2026-08-08

## Repository hygiene, and the security audit made green

### The 5,988 "uncommitted changes" that were not work

VS Code reported hundreds of pending changes on `master`. All of them were a
single untracked directory: `tools/reconstruction-foundry/native/windows-source-helper/target`
— 5,988 files, 3.6 GB of Cargo build output, with **no tracked file under
`native/` at all**.

The crate ships the standard `cargo new` ignore rule, `/target/`, anchored to
its own root. That rule is *tracked content*: it exists only while a branch
containing the crate is checked out. The crate lives on
`feature/diary-p0-slice-3`; on `master` the rule disappears while the untracked
artifacts stay on disk. Only a **root-level** rule survives every branch switch,
so `tools/**/target/` was added to `.gitignore` (`f098e6bf`). Verified
`git ls-files | grep -E '(^|/)target/'` returns 0, so no tracked file is
orphaned by the pattern. The 3.6 GB was retained on disk by the owner's
decision — it is now invisible to git either way.

### Stranded work recovered from 14 worktrees

The repo carries 62 worktrees. **15 held uncommitted work**, six of them at a
*detached HEAD* — the one state where no ref protects the work. Among them:
a new database migration (`0019_onboarding_audit_events.sql`) with
`clerk-onboarding.ts` and its test; new `SyntheticTradesHallFacade.tsx` and
`synthetic-grand-hall-stand-in.ts` with tests; an in-flight recast of the live
`/fresh` homepage.

Each was snapshotted to a `rescue/*` branch **without touching the worktree**:
copy the worktree's index to a temp file, stage into that copy, then
`commit-tree` parented on the worktree's current HEAD and `update-ref`. The
work becomes permanently reachable while the worktree's index, HEAD, and files
stay byte-for-byte unchanged — verified by re-reading each dirty count after
the snapshot. Nothing was deleted.

Five fully-merged local branches were removed. A sixth,
`codex/venue-operating-system-release`, was refused by `git branch -d` because
it is merged to HEAD but *ahead of its own upstream*; left in place rather than
forced.

### Dependency security — 19 advisories to zero

`pnpm audit --audit-level=moderate` (CI's exact command) reported **19
vulnerabilities: 18 high, 1 moderate**. Two scoping errors are worth recording,
because each hid part of the problem:

- An initial `pnpm audit --prod` reported only 11. **CI audits dev
  dependencies too.** `--prod` is the wrong scope for predicting CI.
- An initial survey of `packages/*` missed `tools/twin-forge`.
  `pnpm-workspace.yaml` declares **`packages/*` and `tools/*`** — seven
  manifests, not four. `tools/twin-forge` still pinned the vulnerable
  `sharp@0.34.5`, which kept the advisory alive after the foundry was fixed.

**The dominant failure mode was stale overrides, not missing ones.** Six
existing `pnpm.overrides` entries were *pinning packages to versions that had
since become vulnerable* — each correct when written (see 2026-05-09 for the
original `fast-uri` floor), each since rotted into the thing blocking the fix.
Bumping a parent library could not have helped; pnpm was faithfully forcing the
old version everywhere.

The final advisory needed a non-obvious fix. `sharp@0.34.5` survived
transitively via `tools/twin-forge → @gltf-transform/functions@4.3.0 →
ndarray-pixels@5.0.1`. A blanket `sharp` override would have been wrong:
**sharp uses 0.x versioning where the minor number is the breaking change**,
and `ndarray-pixels@5.0.1` declares `sharp: ^0.34.0` — forcing 0.35 would
violate its author's stated compatibility. Instead `ndarray-pixels` was pinned
to `5.2.0`, which declares `sharp: ^0.35.0` itself and still satisfies
`@gltf-transform/functions`' `ndarray-pixels: ^5.0.1` range. The CVE clears
without overriding any package against its declared constraints.
