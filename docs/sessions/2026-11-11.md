# Session log — 11 November 2026

## A long name on the floor (T-694)

The request: `users.name` is `varchar(200)`, but the floor's records keep the acting person's name in
`varchar(160)`, so for an account named with 161 to 200 characters "every observation tap on the Day
Board and every request step (acknowledge, accept, resolve) returns a 500". Done: "a 200-character name
records an observation and moves a request without error, stored clipped to 160, with tests that fail
before the change."

### What the code showed

The three inserts named in the request (the observation, and the request history row on creation and on
every step) were not the only places a long name was refused. On the same paths:

- creating a request also writes `requests.requested_by_name` (160) and the thread's first message,
  `messages.author_name` (160), before or beside the history row;
- accepting, and resolving a request nobody had taken, write `requests.owner_name` (160) before the
  history row; a handover writes the relief's name, read from `users.name`, to `handover_to_name` (160);
- the handover picker (`GET /venues/:venueId/handlers`) parses every handler through
  `VenueHandlerSchema.name.max(160)`: one colleague with a long name answered 500 to the whole venue's
  picker (probed: Zod `too_big`, maximum 160, at `[1, "name"]`);
- in the request's thread, sending a message writes `messages.author_name`; marking a message read
  answers with `recipientName.max(160)`; and once a long-named colleague had opened the thread, its
  author's own message list carried their receipt and answered 500.

### What changed

`packages/api/src/utils/clip-name.ts` (`clipName`, `RECORD_NAME_MAX = 160`) keeps a name whole when it
fits and otherwise keeps the longest run of whole characters within 160. It is applied at each write and
read above: `services/observations.ts`, `services/requests.ts` (create, transitions, picker) and
`services/conversations.ts` (`appendMessage`, which writes every message, and both receipt producers).
No migration: the columns are unchanged and no stored value changes.

Counting: PostgreSQL `varchar(n)` in a UTF8 database counts code points, and so does Zod 4.6.7's string
`max` ("Strings are measured in Unicode code points, not UTF-16 units", `zod/v4/core/checks.js`; measured:
81 astral characters, 162 UTF-16 units, pass `max(160)`). `clipName` therefore counts code points and
cuts between graphemes. A plain `.slice(0, 160)` counts UTF-16 units: it never refuses, but where the
160th character lies outside the Basic Multilingual Plane it leaves half a surrogate pair, which
PostgreSQL keeps as U+FFFD (shown below).
