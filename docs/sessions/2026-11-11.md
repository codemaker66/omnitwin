### A test this audit added was racy

`HallkeeperPage.offline-queue.test.tsx`, which came in with #370, failed #390's Test job once ("expected 1 to be greater than 1" at line 524). The test sends `visibilitychange` the moment a row appears. The page attaches that listener in an effect, and React runs a commit's effects one turn of the event loop later whenever the commit's task ran past the scheduler's 5 ms; testing-library resumes the test on a zero-delay timer, which can come first. The event then reaches nobody. It is a race in the test, not in the product: in a browser the gap is milliseconds after a read that has just happened. Reproduced here by holding the loop for 2 ms after the row appears, which fails the case every time with CI's own message. The fix (the test's helper waits one turn of the loop before sending) is written and has no pull request yet. `HallkeeperPage.release.test.tsx` had already met the same gap and worked round it. Sixteen web test files send such events; fourteen were not checked.

### Lessons

- `gpu-scope.mjs` needs full commit ids. Given a short base it fails closed and says the gate is required, for the reason "no comparable base commit". Read the reasons, not only the answer. Misreading it split one pull request in two for nothing.
- A suite that prints "skipped" has not run. #385 passed review and then failed CI on a suite that skips on this PC unless its own database is running; the lead had counted its skipped cases as unrelated.
- Instrumentation changes timing. The first attempt to reproduce the test race passed only because the trace's own extra `await` was the fix.
- A busy-wait in a test must not read `performance.now()`: under fake timers that clock stops, the loop never ends, and stopping the task does not kill the worker.
- A decision carried forward in a summary can be stale. The Grand Hall question was asked again after Blake had answered it; the note of record, not the summary, is what to check before asking.
