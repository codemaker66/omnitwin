# 24 September 2026

## T-629 — application performance review

Blake asked to look at increasing performance across the app and find what is
missing. Four read-only audits (API/database, React rendering, 3D rendering,
page load) ran against `d7eb71b`; each finding was checked against source before
any change. The native splat renderer, its workers and generated data were
excluded: T-627/T-628 own them and public splats remain on hold.

Implemented on `claude/cool-tesla-90zlcp`, with measurements and the ranked list
of remaining opportunities in the
[performance review](../reports/performance-review-2026-09-24.md):

- Web bundles: side-effect-free shared contracts, named Sentry imports, on-demand
  GDTF/MVR archive reader, and a separate `three-webgpu` vendor chunk. The
  panorama tour's route payload fell from 633 KB to 329 KB gzip; the homepage's
  from 175 KB to 75 KB; the deferred Sentry chunk from 144 KB to 26 KB.
- Homepage and hallkeeper images now come from display-sized WebP ladders of the
  same supplied photographs; throttled phone LCP 24.9 s → 5.1 s and transfer
  7.34 MB → 0.97 MB on the local production build. The crest is a 21 KB WebP.
- `vercel.json` caches versioned models and hashed voice clips immutably and
  other public files briefly. The quiz no longer fails when Google Fonts is
  unreachable (reproduced before, rendered after).
- Planner: fewer per-frame store notifications and re-renders during drags and
  marquee selection; hidden wall click planes; fades rebuild materials only on a
  blending change; Grand Hall textures survive camera gestures. The desktop
  placement-rule sweep that runs on every drag move is grid-indexed
  (1,287 items: 209.6 → 1.45 ms, identical results under a 500-layout property
  test), and select-all drags no longer rescan the layout per item. The
  Diary's render and drag costs were reduced in a separate commit.
- API: one-statement fast path for linked sign-ins; optional networkless Clerk
  verification (`CLERK_JWT_KEY`); CORS preflight caching; JSON/text response
  compression with binary routes opted out; 60 s Neon idle connections;
  set-based planner batch saves (150 objects: 158 → 11 statements).

Decisions and constraints recorded in the report: no change to planner render
resolution (a prior founder-reviewed choice), furniture model simplification or
transmission glass without visual acceptance, or splat-owned data. Layout
revision retention is a data-retention decision left open.

Verification used disposable PostgreSQL 16 clusters on the suites' own loopback
ports (55476–55478), never a shared database. Results are in the report.

Blake then asked for the best choices for maximum performance and a push to
`master`. No other release was active (master unchanged since `d7eb71b`; open
PRs target `release/r1` or are documentation). Before pushing, the production
build ran the planner, tour, hallkeeper, quiz, landing, pricing and navigation
E2E specs in `vite preview`; every failure also occurs on the `master` build in
this container (details in the report). The push to `master` was then refused
by this session's permission system, so the branch waits for Blake's decision.
Live verification is also not possible from here: the session's network policy
blocks `venviewer.com` and `api.venviewer.com`.

The founder mandate rules out a lower-resolution canvas, blurred motion and
visibly simpler furniture, so "maximum performance" here means invisible work.
Measured and rejected: error-bounded furniture simplification removes under 5%
of triangles at 0.5 mm (texture and normal detail sets the budget), and
distance-based detail levels only reach about 2× at errors that are sub-pixel
beyond 20 m. The next wave (instanced place settings, merged Grand Hall
ornaments, a mounted room shell, a direct furniture instancing path, cached
name plates, self-hosted fonts, display-sized images, earlier staff code
download, a faster planner start-up and API hot paths) follows in later commits.

Defects found in passing and left open are listed in the report (Diary enquiry
tray window, phantom template selection, instanced furniture culling); the next
wave addresses them.

### Second wave

Six agents worked in isolated worktrees; each commit was reviewed, integrated
on the branch and re-verified. Measurements and the full list are in the
report's "Second wave" section.

- Planner: dinner covers share one geometry and material per part (1,000 → 5
  each; select-all drag commit ≈24 → ≈7 ms); editable furniture draws from
  pooled instance buffers (drag-step commit 65 → 8.1 ms at 1,287 items); opaque
  Grand Hall ornaments draw as merged batches (overview 330 → 124 draws on the
  integrated branch, 115 after T-630); the
  room shells stay mounted across camera gestures; name plate textures are
  shared. Instanced covers were built and rejected: they changed 148–2,082
  pixels per view. Merged ornaments differ in 1–41 isolated edge pixels per
  frame (float rounding); fades, x-ray and section views are pixel-identical.
- Loading: guarded staff pages download their code during the account check;
  the planner's draft lookups run together and a guest's chosen draft is not
  fetched twice; fonts are self-hosted; quiz and inventory images are
  display-sized.
- Fonts: `packages/web/scripts/self-host-google-fonts.mjs` mirrored Google's
  own files and rules (42 browser user agents probed); `provenance.json` and
  the OFL licences sit in `packages/web/src/styles/fonts/`. Firefox on Windows
  (faces without `MVAR`) and macOS (the static EB Garamond italic instance) keep
  their builds as user-agent overrides; Apple and Android builds differ only in
  tables those platforms do not use. Opera and Vivaldi on Windows, Yandex, Edge
  for Android and Firefox on Windows 7/8.1 were served static instances and now
  get the variable faces as designed. Font preloads were measured and rejected
  (render-blocking in Chrome).
- Images: `packages/web/scripts/build-image-ladders.mjs` (sharp, Lanczos3 on
  premultiplied alpha, near-lossless WebP) writes deterministic copies with a
  `provenance.json`. The cleaned room plans stay PNG: a re-encode would drop
  their C2PA manifest recording them as AI-generated.
- API: rate limiting per verified user (it was per office IP) and 429 instead of
  500 when limited; access checks skip stored thumbnails; the Diary tray asks
  for open enquiries, newest first, for its venue; phase-graph payloads are
  omitted for the web; linked-layout summaries are batched with a fallback for
  an older API; dashboard totals are computed in SQL; migration 0071 adds two
  foreign-key indexes. A pipeline above £1,000,000 no longer makes the
  dashboard answer 500. The Neon connect timeout was withheld: driver 0.10.4
  can crash the process on a stalled handshake.

Still open: device frame measurements, compressed furniture downloads, and the
master push, which needs Blake. (The Enquiries list was fixed afterwards as
T-632, below.)

## Follow-up fixes from the T-629 defect list

Blake sent three of the defects found in passing back as tasks.

- T-630, window glass. Surface fades replaced every material's opacity with
  the surface opacity, so at rest the arched-window glass (authored 0.42 and
  0.38 over an emissive daylight backing) drew opaque. Fades now scale each
  material's authored opacity, read once per material, so the glass stays
  translucent at rest and fades with its wall; opacity only takes effect on a
  transparent material, so opaque and full-opacity materials (the dome shell)
  behave as before. The merged stand-in keeps each translucent piece as its own
  object on its original transform, which sorts exactly like the per-mesh pane,
  and translucent draws no longer split opaque batches (overview 124 → 115
  draws). The frieze figures and underlight strip run across the window
  openings between the backing and the glass, so they now show through the
  glass at rest, as they already did during fades; removing them from the
  openings would change the ornaments and is left to Blake.
- T-631, wall replay. Every camera gesture hid the detailed shell and, when it
  returned, the brick wall restarted from a whole wall and replayed its
  disassembly (the kept-mounted shell copied the old remount on purpose). A
  hidden wall now writes no matrices and requests no frames but keeps its click
  animation's time on the frames that are drawn, exactly as the wall's
  ornaments (drawn throughout) keep theirs, so it reappears in step with them.
  The lean shell drawn during a gesture no longer shows a click-controlled wall
  whole; phones use only the lean shell and keep their behaviour.

Evidence: `docs/reports/assets/planner-follow-ups-2026-09-24/` holds the
before/after sheets: the ornament harness (3ac700f against the fix at identical
poses and frame steps: at rest, a camera-driven fade from behind the wall at
40 %, a clicked disassembly at 1.2 s), the real planner at rest, and the real
planner sequence (click the window wall away, orbit and release twice, click it
back) in which the committed code replays the disassembly 4–10 s after each
release and the fix does not. Software rendering runs the 5 s animation several
times slower in wall-clock time; the frame deltas it uses are clamped as in
production. The new tests fail against the previous code.
- T-632, dashboard enquiries. The list asked for the API's default page, the
  20 least recently updated enquiries, oldest first. It now pages newest first
  by creation (20 at a time, "Show N more", "Showing 20 of 57 enquiries,
  newest first"). Each show-more re-reads the last five listed rows and
  continues after the latest one it finds, so an enquiry created meanwhile is
  not repeated and one that left the filter is not skipped; when that cannot
  be proved the view says the list changed and offers a reload. Late responses
  from an earlier filter or reload are discarded, a failed first page says so
  instead of "No enquiries found", and the Diary tray's existing call is
  unchanged. The API echoes the order it applied, so a web build that reaches
  the old API first pages in its old order without claiming "newest first".
  Migration 0072 adds `(venue_id, created_at, id)` and
  `(venue_id, state, created_at, id)`; on disposable PostgreSQL 16 with 20,000
  enquiries in one venue a page read 1,694 buffers before and 28 after, and a
  rare status needed the second index (20,277 → 16). A worktree agent built it;
  I reviewed the diff and screenshots, cherry-picked it and re-ran the API unit
  suite, the platform PostgreSQL gate (76/76 on a fresh local cluster with
  0072 applied), the web suite and its new Playwright spec on the integrated
  branch; `enquiries-list-before-after.webp` in the evidence folder shows the
  list before and after. Ordering by creation is a proposal for Blake; newest
  activity first would need an `updated_desc` order and index. At 390 px the
  page still scrolls sideways (the status tab row does not wrap), as before.

## T-633 — the Enquiries desk

Blake saw the T-632 list and called it ugly, "not next gen", and daunting for
someone working in it all week. He asked for a polished, luxurious, intuitive
tool for veteran venue bookers that makes finishing tasks feel good,
suggesting game design and psychology, and said to rebuild it if confident. The
rebuild is on `claude/cool-tesla-90zlcp`. The design, the research mapped to each
decision, four image-generation prompts for exploring alternatives, the
decisions left for Blake and the evidence are in the
[design record](../design/enquiries-desk-2026-09-24/README.md).

- The desk follows the selected Inventory reference:
  - **Surfaces:** the sage ground, an ivory sheet with a tilted edge, the stage counts on a copper plane, and a forest decision panel with a fixed inner frame.
  - **Stage counts:** they are also the filters. `countEnquiryStages` reads six one-row pages; a change made here moves the counts at once, then they are re-read.
  - **Opening sentence:** built from those counts, it names the new enquiries and the oldest one's wait.
  - **Ledger:** grouped by venue-local arrival day and led by an event-date tile.
  - **Panel:** it sits beside the list from 1180 px and pictures the requested room from Trades Hall's supplied photographs, only when the venue is Trades Hall under either of its two known slugs.
- **Status changes:**
  - Start review happens at once, since it sends nothing to the client.
  - Approve and Decline confirm inline and say what each emails. Approval and decline both email the client, and a decline note is quoted in the email as "Note from the events team" (`packages/api/src/routes/enquiries.ts`, `email-templates.tsx`); the old modal said neither.
  - A 422 from a conflicting change re-reads the enquiry and says where it now is.
- **Hover spring:** `index.html`'s global cockpit spring scaled every button 6% on hover, so list rows swelled under the pointer. It now has a `[data-calm-controls]` opt-out wrapped in `:where()`, which leaves the global selectors' specificity unchanged; only the desk uses it.
- **Focus rings:** the desk draws its own ink or cream rings, because the global cyan ring is about 1.4:1 on ivory.
- **Contrast:** measured for every text pair and control state. All pass WCAG AA; the lowest text pair is ink-3 on the selected row at 4.59:1, and large numerals, graphics and focus rings are at least 3:1.

Verification (mocked-API browser harness at 1440, 1024 and 390 px, with no sideways scroll at 390):
- The unit suites for the desk, formatting, paging and dashboard source guards pass. Two deliberate mutations (approval without confirmation, stepping that stands still) each fail a test.
- The Playwright spec `e2e/enquiries-list-paging.spec.ts` passes 3/3 in Chromium, with the triage run at 1440 px. It runs through a scratch config that points Playwright at the container's preinstalled Chromium, because the pinned version expects a newer headless shell.
- The status stamp runs on the panel and row chips and does not run under reduced motion (`getAnimations()`).
- The before/after uses the same enquiries on the previous commit.
- Full web suite: 518 files, 6,704 tests pass (16 skipped). Web typecheck (app and e2e) and lint pass.
- `vite build` passes. It needs a `pk_live_` Clerk key, so it used the session's placeholder (`clerk.example.com`); nothing from that build is deployed.
- Build size: the dashboard chunk is 271 KB (68.7 KB gzip) and its CSS 72 KB (14.5 KB gzip). At the end of wave 2 they were 241 KB (59.5 KB gzip) and 50 KB (10.1 KB gzip), a figure that also includes T-632.

Decisions for Blake are listed in the record: newest first, review without confirmation, the session tally and the greeting by first name. His aesthetic verdict is pending, and release waits with the rest of the branch.
