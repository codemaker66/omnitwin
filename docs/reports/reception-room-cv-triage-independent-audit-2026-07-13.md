# Independent audit: Reception Room computer-vision triage

**Date:** 2026-07-13  
**Scope:** `tools/reception-hd/triage_fixed_views.py`, its eight focused tests, the committed JSON report, the 42 saved fixed-view PNG files, and direct visual inspection of the overview and ceiling pairs.  
**Code changes:** none. This audit adds only this report.

## Bottom line

The tool works as a **warning system** for the current fixed screenshots. It consistently sends all six known parent-plus-child renders to human review, and it leaves all six Quality PLY-versus-leaf renders clear. The report reproduces byte-for-byte in the current Python environment.

In ordinary language: the broken setup draws the room twice and makes edges look
swollen, faint or doubled. The checker found that problem in every tested view.
Loading only the correct leaf asset removes that visible failure. The SOG leaf
also stayed extremely close to the full-quality PLY in these six screenshots, so
this test found no evidence that this particular PLY-to-SOG step is the main
source of softness. It still cannot tell us whether detail missing from both
files was lost earlier during capture or reconstruction.

That result does **not** prove that the Quality render is HD, better, physically correct, or safe to release. It only proves that none of this tool's configured warning signals crossed their thresholds. The code and README generally say this clearly.

Two limits matter most:

1. The JSON report contains image names but not image hashes. It is therefore not a self-verifying evidence receipt. Someone could replace a PNG while leaving the old JSON beside it.
2. The thresholds were checked on the same diagnostic images they separate. They have not been calibrated on an independent set of good and bad renders. A local defect or a faint ghost can pass.

These are blockers if the JSON is used as release approval or formal proof. They are not blockers for its stated use as a local, human-in-the-loop warning system.

## What the current evidence proves

- All 42 saved images are readable 1200 x 900 RGB PNG files.
- For `mobile-sh0-spz-leaf` versus `mobile-sh0-spz-all-invalid`, all six views return `review`.
- Those six views have missing-edge fractions from 0.555686 to 0.687648, extra-edge fractions from 0.456157 to 0.588407, and nearby-parallel-edge fractions from 0.365165 to 0.430913. All three configured edge warnings fire in every view.
- For `quality-sh3-ply` versus `quality-sh3-sog-leaf`, all six views return `triage_clear`.
- The saved report can be regenerated byte-for-byte from the current images and environment. Both copies have SHA-256 `48D82B9836A2B87DCBB7C53745E59A70EC43FD70ABE904232DA0C6639F4737A2`.
- Direct visual inspection agrees that the parent-plus-child render has a broad soft/smeared appearance compared with the leaf-only render. The Quality PLY and Quality leaf images are visually very close in the inspected views.

The computer-vision result alone does not identify why the pixels differ. Calling the defect “parent-plus-child double drawing” also relies on the independently known asset membership. A camera change, renderer change, or legitimate geometry change can produce the same warning signals.

## What it cannot prove

- It has no source photograph, survey control, E57 geometry, or other independent truth reference.
- `triage_clear` means “no configured alarm fired,” not “good,” “HD,” “more detailed,” or “physically accurate.”
- The six screenshots use different aim directions and fields of view but the same optical centre. They do not test walking through the room, popping, view-dependent colour, or motion stability.
- The Quality result measures similarity to the chosen PLY baseline. A defect shared by both images is invisible.
- Full-frame measurements dilute small but important defects. There are no masks for doors, moulding, floor seams, text, or other high-value regions.
- There is no independently labelled calibration set, repeated-capture noise floor, false-positive rate, false-negative rate, or held-out threshold test.

## Findings

### 1. High: the report is not bound to its evidence

The JSON stores basenames and package versions, but it does not store a SHA-256 hash or byte count for each input image. It also omits the repository revision, Python version, operating system, browser/WebGL/GPU details, asset hashes, camera parameters, device-pixel ratio, and capture time. The current report can be reproduced while the current files remain in place, but the report cannot later prove which image bytes or rendering build produced it.

**Required before treating it as a formal evidence receipt:** add a manifest containing every input hash, byte count, dimensions, baseline/candidate role, camera and viewport settings, source asset hashes, capture-tool/build identity, and report-tool/build identity. Hash the canonical manifest and report together.

### 2. High if used for acceptance: thresholds are diagnostic and in-sample

The report explicitly says its thresholds were checked on this diagnostic capture, not an independent benchmark. The closest Quality result is a nearby-parallel-edge fraction of 0.261180 against a review threshold of 0.28, a margin of only 0.018820. The current pair separation is real, but it is not a general accuracy estimate.

On the real Quality overview image, additional in-memory stress checks produced these results:

| Exact candidate transformation | Verdict | Important result |
|---|---:|---|
| Shift the whole image 1 pixel right with `numpy.roll` | clear | no warning fired |
| Shift the whole image 2 pixels right with `numpy.roll` | clear | no warning fired; this is the configured tolerance |
| Shift the whole image 3 pixels right with `numpy.roll` | review | missing, extra, and nearby-parallel edges fired |
| Blend 80% original plus 20% copy shifted 6 pixels | clear | nearby-parallel fraction 0.176; no warning fired |
| Blend 70% original plus 30% copy shifted 6 pixels | review | missing-edge fraction 0.404 fired |
| Replace a centred square covering 5% of the frame with black | clear | changed-pixel fraction 0.050 and RGB MAE 0.017 |
| Gaussian-blur the whole image with sigma 1.0 pixels | clear | missing-edge fraction 0.385, just below 0.4 |
| Gaussian-blur the whole image with sigma 1.5 pixels | review | missing-edge fraction 0.580 fired |

These are not contradictions in the code: the tool promises conservative triage, not complete defect detection. They do show why `triage_clear` must never become an approval label.

### 3. Medium: capture repeatability is unmeasured

The capture script waits for a `loaded` flag and then waits one second. There is no saved GPU completion proof and no repeated capture of the same variant and camera. A repeat set is needed to measure normal renderer variation before interpreting small differences. The current Quality pair's edge-distance 95th percentiles are 6 to 8 pixels even though the edge-match tolerance is 2 pixels; the aggregate fractions stay below the review thresholds, but the mismatch is not zero.

### 4. Medium: refusal tests are useful but narrow

The code correctly refuses a clear result when the **baseline** is flat, full-amplitude random noise, too sparse, too dense, or unstable after blur. It also fails closed on different image dimensions and non-finite arrays. The automated tests cover flat and one kind of random-noise baseline, but not low-contrast noise, compression artefacts, crop/scale changes, colour-profile changes, or near-threshold cases. Candidate coherence is reported but is not itself a verdict guard.

## Safe wording for people reading the result

Use:

> All six known invalid parent-plus-child screenshots triggered the configured edge warnings. All six Quality leaf screenshots stayed within those warning thresholds relative to the Quality PLY baseline. A person must still review them, and this is not proof of HD detail or physical accuracy.

Avoid:

> Computer vision proved the Quality model is better, HD, or physically correct.

## Decisive next checks

1. Bind every screenshot and capture setting into a hashed evidence manifest.
2. Capture each exact camera at least three times to measure renderer noise and settling.
3. Calibrate thresholds on a separately labelled set that includes faint ghosting, local missing objects, blur, colour drift, camera movement, and legitimate geometry changes.
4. Add region-level checks for doors, floor seams, moulding, columns, and other important details; keep human inspection.
5. For actual quality acceptance, compare registered renders with rights-cleared photographs that were not used for training, plus moving views and metric geometry checks.

## Same-day remediation addendum

The audit findings above describe the original v1 tool. They were subsequently
used as failing cases for the backwards-compatible v2 report extension.

The hardened tool now:

- hashes every PNG it actually reads and includes size, dimensions, format, and
  comparison usage;
- hashes and verifies the fixed-view manifest when one is supplied;
- binds the tool source, Python/platform details, package versions, all metrics,
  and the evidence records into a canonical SHA-256 report receipt;
- fails closed when a supplied manifest's screenshot hash or size is stale; and
- adds one human-review signal with local 2x2/4x4/8x8 checks and gradient-energy
  checks at 0, 1.2, and 2.4 pixel scales.

The exact real-image stress cases that previously returned `triage_clear` now
return `review`: the 20%-opacity copy shifted by 6 pixels, the centred black
square covering 5% of the frame, and Gaussian blur with sigma 1.0. Flat and
full-amplitude random-noise baselines still return `not_assessable`. None of
these changes turns the tool into product acceptance or a physical-truth test.

The real report binds 24 actually used PNG files and verifies all of them
against the supplied fixed-view manifest. Two clean replays were byte-equal.
The v2 report file SHA-256 is
`F14A6D9F5B64318044BBA8D40BA08956F51A67629E321F5AB3E20BEE2AFD39BA`;
its canonical content receipt is
`AF2979E166B9A3DD3358B93AB29CCCEB44583C04EC8B55F612278EFABD490689`.

## Plain-language visual evidence addendum

The v2 numbers now have a deterministic visual companion:
`tools/reception-hd/render_triage_report.py`. For every checked view it produces
one lossless three-panel board: the baseline, the candidate, and a difference
map. Review results use an orange **computer-vision warning — human review
needed** banner. Clear triage results use a neutral **no configured warning
crossed its limit; not an approval** banner. This avoids presenting a clear
triage result as approval.

The renderer rechecks the v2 report receipt and the exact screenshot hash,
size, dimensions, mode and declared comparison role before drawing anything.
It reruns the measurements rather than trusting stale stored metrics. Output
indexes contain basenames and hashes, not the caller's private screenshot
folder. Path traversal, stale metrics, unsupported schemas, altered report
bytes, altered screenshots and mismatched dimensions fail closed.

The real Reception Room evidence set contains 12 boards: six review boards for
the invalid parent-plus-child comparison and six clear-triage boards for the
Quality PLY-versus-leaf SOG comparison. The final overview board SHA-256 values
