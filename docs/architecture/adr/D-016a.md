# D-016a — Training environment: PyTorch 2.14.1 and gsplat main, with PPISP on trial

Status: accepted for the environment (validated 2026-10-16, T-655). PPISP stays an opt-in trial: inconclusive at one seed under the rule below.
Date: 2026-10-13 (target revised 2026-10-14; validated and trial judged 2026-10-16)
Authors: Blake (direction), Claude (T-655)
Supersedes: D-016's trainer environment pins only (gsplat 1.5.3, PyTorch 2.4.1, CUDA 12.4), for new training. D-016's decision that splat training runs on RunPod stands, and old recipes keep their old pins.
Depends on: D-016, D-006a

## Context

Blake, 13 October 2026, verbatim: "Upgrrade the splat and pytorch to the latest and inform our repo we are doing so, multiple sessions may need that info. Try PPISP."

What "latest" meant, checked at the source:

- PyTorch 2.14.1 (PyPI, 30 September 2026) with torchvision 0.29.1. The official Linux wheels come in cu126, cu130 and cu132 builds; PyPI's default is the CUDA 13.0 build.
- gsplat's newest release is still 1.5.3 (4 July 2025). GitHub `main` is ahead: `512d366b67073d77ca099ede742683c165dfc23b` (19 September 2026, version string 1.6.0, unreleased, still the head on 14 October). It carries the PPISP post-processing in `examples/simple_trainer.py` (`--post_processing ppisp`, pinning `ppisp@v1.2.1`) and, since July 2026, PPISP with the MCMC strategy.
- PPISP (NVIDIA, CVPR 2026, arXiv 2601.18336, `nv-tlabs/ppisp`, Apache-2.0) models per-frame exposure and a colour homography, per-camera vignetting and a camera response curve, plus a controller that predicts exposure and colour for views it never saw. Its newest tag is v1.3.0 (`a247368047651db2e03e6f97a36e4f5bebbe5c5f`, 23 September 2026): the same API as v1.2.1 with faster kernels, an exact CRF backward and a fix for misaligned pixel coordinates.

Why the CUDA 13.2 build (revised 14 October). CUDA 13.2 Update 2 fixes a compiler bug present since CUDA 12.8: compiler-inserted thread reconvergence could fail and leave stale or corrupted values in registers, in kernels with two or more nested levels of thread divergence ([NVIDIA CUDA 13.2 Update 2 release notes](https://docs.nvidia.com/cuda/archive/13.2.2/cuda-toolkit-release-notes/index.html), resolved issue 6111901; its nvcc is 13.2.86). PyTorch 2.14.1 moved only its CUDA 13.2 Linux builds onto 13.2.2 ([v2.14.1 release notes](https://github.com/pytorch/pytorch/releases/tag/v2.14.1), #196351); its cu126 and cu130 builds come from affected toolkits. Nobody has tested whether gsplat's or PPISP's kernels contain the pattern, but a rasteriser backward with per-pixel early exits inside tile loops has its shape. The first T-655 pod built gsplat with nvcc 13.0.88, inside the affected range, so that build is discarded.

The panorama splat lane does not train through the `omnitwin/trainer` image. Its pods use RunPod's own PyTorch image and install gsplat at boot (`D:/claude/pano-splat-20261003/pod_boot.sh`: `runpod/pytorch:2.4.0-py3.11-cuda12.4.1-devel-ubuntu22.04`, `gsplat==1.5.3` compiled on first use for sm_90). CUDA 12.4 predates the bug.

## Decision

The environment for new splat training (validated 16 October 2026, below):

| Component | Target pin |
|---|---|
| PyTorch / torchvision | 2.14.1+cu132 / 0.29.1+cu132, official `cu132` wheels (`https://download.pytorch.org/whl/cu132`), built with CUDA 13.2.2 |
| CUDA toolkit for the extensions | 13.2 Update 2 (nvcc 13.2.86) or newer; never 12.8 to 13.2 Update 1 |
| Host driver | 580 series or newer: CUDA 13.x builds run on drivers 580+ under minor-version compatibility (NVIDIA's table). RunPod `allowedCudaVersions: ["13.0"]` selects such hosts. |
| gsplat | built from source at `main` `512d366b67073d77ca099ede742683c165dfc23b` with nvcc 13.2.86 (`--no-build-isolation`, `BUILD_EXPERIMENTAL=0`) |
| PPISP | `nv-tlabs/ppisp` v1.3.0, `a247368047651db2e03e6f97a36e4f5bebbe5c5f`, built with nvcc 13.2.86 (`--no-build-isolation`) |
| fused-ssim (trainer image only) | built with nvcc 13.2.86 |
| Python | 3.12 |

Fallback: if a 580-series driver cannot run the cu132 wheels, use the cu130 wheels with every extension still built by nvcc 13.2.86 or newer (an open gsplat pull request, #1085, reports torch 2.14.1+cu130 building against CUDA 13.3). If the fallback is used, it is recorded here.

PPISP is an opt-in trainer flag in the trial; default recipes do not change.

3DGUT needs a separate build. The trainer uses gsplat's classic 3DGS rasterization only, so the trial builds gsplat with `BUILD_3DGUT=0`, which leaves out the 3DGUT ("from world" / unscented-transform) kernels. Those kernels took about 35 of the full build's 40 minutes on the first pod. Work that needs 3DGUT builds gsplat without that flag.

## Validation status (16 October 2026): environment validated

- First pod (13 October; RunPod H100 SXM, driver 580.126.09): PyTorch 2.14.1+cu130 ran on the GPU, and gsplat `main` @ `512d366b` compiled in full with nvcc 13.0.88 (2,418 s). That compiler is in the affected range, so the build was discarded. The pod stopped at 23:27 UTC for a reason never established (no logs could be retrieved; RunPod refused a CPU-only resume) and was terminated on 16 October.
- Trial pod `eexytqnlp25mg2` (15–16 October; RunPod H100 80GB HBM3, driver 580.126.09, image `runpod/pytorch:1.4.0-cu1300-torch2130-ubuntu2404`), all checked in its logs:
  - CUDA 13.2 Update 2 toolkit (`cuda-toolkit-13-2=13.2.2-1` from NVIDIA's apt repo, 219 s): `nvcc` V13.2.86.
  - torch 2.14.1+cu132 and torchvision 0.29.1+cu132 passed a CUDA operation on the 580 driver, so the cu130 fallback was not used. cuDNN 9.24.
  - gsplat `512d366b` (1.6.0, `BUILD_3DGUT=0`) built in 119 s and PPISP v1.3.0 in 40 s. Both build logs show `/usr/local/cuda-13.2/bin/nvcc` as the compiler.
  - PPISP's own test suite passed: 235 tests. The environment check passed: gsplat forward and backward, SelectiveAdam, MCMC, PPISP forward and backward, LPIPS, GPU JPEG decode. 200-step smoke runs of both arms passed.
  - The fx_ctrl60k recipe ran at 21–25 steps/s, against 19.6 in the old environment.
  - Equivalence to the old environment (rule below): the new-environment control scored 22.522 dB on the headline against the old environment's 22.535 dB, a paired difference of −0.013 ± 0.079 dB over 30 faces (t −0.9; raw −0.020 dB). That is within 0.10 dB, so the two are equivalent.
- The first boot of the trial pod failed in 4 s. Installing NVIDIA's `cuda-keyring` package on top of the `cuda.list` source the image already carries makes apt refuse (`Conflicting values set for option Signed-By`). Use the image's existing source and add the keyring only when no NVIDIA source is listed. `infra/runpod/RUNBOOK.md` and the Dockerfile record this.
- The RunPod image pins (`infra/runpod/Dockerfile`, template, runbook, healthcheck, bundle contract) now describe `omnitwin/trainer:gsplat-512d366b-pt2.14.1-cu132`, built from `pytorch/pytorch:2.14.1-cuda13.2-cudnn9-devel`. The build refuses any nvcc other than 13.2.86. That image has not been built or pushed yet; until it is, pods use the plain-image path in the runbook, which is the path validated here. Old recipes keep `omnitwin/trainer:1.5.3-cu124`.

## T-655 trial decision rule (pre-registered 14 October 2026, before the trial pod)

Arms, one seed each, sequential on one pod: the panorama lane's no-skin control recipe (fx_ctrl60k: 60k steps, held-out sweeps 7, 22, 33, 36 and 43) in the new environment, and the same recipe with `--ppisp`. Scores are on the 30 held-out faces at 4096 px, inside the training mask.

Decisive readings, with no colour fitted to the test photos:

1. PPISP's controller path (exposure and colour predicted from the render alone) against the control's raw render: face-mean PSNR, LPIPS and the paired per-face difference.
2. The same comparison per region for the ceiling, the floor, and glass (the trainer's no-LiDAR class: windows, glass and outside). These are where an independent comparison, EvenSplat (arXiv 2610.01876, 1 October 2026), found PPISP weakest: 1.4 dB behind under spatially varying light and 5.0 dB behind under high-contrast light.

Verdict:

- **PPISP helps**: reading 1 gains at least 0.20 dB with at least 20 of 30 faces better, its LPIPS is no worse by more than 0.005, and none of the three regions loses more than 0.20 dB.
- **PPISP hurts**: reading 1 loses at least 0.20 dB, or any of the three regions loses at least 0.50 dB.
- Otherwise **inconclusive at one seed**: no default changes. The next experiments are a second seed and local exposure compensation in EvenSplat's style (re-implemented; no code is published).

Reported but not decisive: the per-sweep colour-fitted headline and the per-face-matched scores, which re-fit colour to each test sweep or face and so hide most of what the controller is for; per-light-state means. One more check decides shipping rather than research: the PPISP arm's raw render is what a viewer without an ISP shows, so if it is more than 0.20 dB below the control's raw render, PPISP cannot ship without a viewer-side correction or bake.

Environment check: the new-environment control against the old-environment fx_ctrl60k (22.535 dB headline, LPIPS 0.2863, built with CUDA 12.4). A difference of 0.10 dB or less on the headline counts as equivalent; a larger one makes the toolchain the first suspect.

## T-655 trial result (16 October 2026): inconclusive at one seed

Pod `eexytqnlp25mg2`, seed 0, both arms on the fx_ctrl60k recipe in the new environment. Scores are on the 30 held-out faces at 4096 px:

| | Old env fx_ctrl60k | New-env control | New-env PPISP |
|---|---|---|---|
| raw PSNR (dB) | 22.160 | 22.140 | 21.908 |
| PPISP controller path, no fit (dB) | | | 22.153 |
| matched PSNR (dB, reported only) | 22.776 | 22.766 | 22.722 |
| sweep headline PSNR (dB, reported only) | 22.535 | 22.522 | 22.369 |
| LPIPS raw (control) / controller (PPISP) | | 0.2916 | 0.2823 |
| LPIPS sweep (reported only) | 0.2863 | 0.2861 | 0.2793 |

Decisive readings:

1. **PPISP's controller path against the control's raw render:** +0.014 dB (paired SD 0.263 dB, t 0.3), with 15 of 30 faces better. LPIPS improves by 0.009 (t −4.2; 26 of 30 faces better).
2. **By region** (PSNR dB / LPIPS):
   - ceiling −0.08 / 0.000
   - floor −0.01 / −0.019
   - glass, no LiDAR: −0.47 / −0.014

Neither the helps nor the hurts conditions hold. The glass region's −0.47 dB is just short of the 0.50 dB hurts line and is the reading to watch in the second seed.

- **Verdict: inconclusive at one seed. No default changes;** `--ppisp` stays opt-in.
- **Shipping check: fails.** The PPISP arm's own raw render is 0.23 dB below the control's raw render (t −4.8; 25 of 30 faces worse), past the 0.20 dB line. A PPISP-trained splat cannot ship unless the viewer applies its correction or the correction is baked into the splat.
- **What PPISP learned:**
  - camera response curves near identity (toe about 1.01, shoulder about 1.10, gamma about 0.98);
  - per-face exposure SD of 0.08 stops;
  - a controller that reproduces the per-frame exposure on the training faces (r 0.94).
- **Next experiments,** as pre-registered: a second seed, and local exposure compensation in EvenSplat's style.
- **Evidence lives outside the repo, in `D:/claude/ppisp-20261013/`:**
  - `RESULTS.md`
  - `results/analysis.json`, the rule's output with paired statistics
  - both arms' run directories
- **Losses:**
  - The PPISP arm's tar, PLY and evening colours match their pod checksums. The control arm's tar matches too, but its 2 GB day PLY is truncated: the pod's post-run self-stop cut the download. So the control model itself is not kept, though its metrics are complete.
  - The control's evening colours came down without a pod checksum.
- **Cost:** T-655 spent about $14.9 of its $20 cap across both pods.

## Consequences

- Old recipes stay reproducible on their own pins (gsplat 1.5.3 on PyTorch 2.4). Results from the two environments are compared as such, not mixed silently.
- gsplat `main` is unreleased, so the commit is the version. Every run records its versions (the panorama trainer writes them to `run_config.json`), and an upgrade past `512d366b` needs a new smoke run.
- CUDA extensions for the trainer are compiled with nvcc 13.2.86 or newer; a build from an affected nvcc (12.8 to 13.2 Update 1) is not used for training.
- CUDA 13 needs a 580-series driver. cu126 wheels remain the fallback for older drivers, but then the extensions need a CUDA 12 toolkit, every version of which from 12.8 is affected, so that path would need a toolkit older than 12.8.
- The RunPod-only rule of D-016 is unchanged. No splat training moves to the local PC.

## Alternatives considered

- **Stay on gsplat 1.5.3 and PyTorch 2.4.1.** No PPISP, and a CUDA 12.4 toolchain that newer PyTorch builds have left behind. Kept only for reproducing old results.
- **cu130 wheels with CUDA 13.0 extensions** (the 13 October target): PyPI's default build, but both come from toolkits with the reconvergence bug. Kept only as the fallback above, with the extensions rebuilt by nvcc 13.2.86.
- **cu126 wheels.** They run on older drivers, but the matching CUDA 12 toolkits from 12.8 on are affected.
- **CUDA 13.3 or 13.4 toolkits.** Newer, but 13.2.2 matches the cu132 wheels exactly; any later toolkit would also have to be checked for the fix.
- **PPISP v1.2.1**, the version gsplat's example pins. Same API; v1.3.0 adds correctness fixes.
- **Waiting for a gsplat 1.6.0 release.** No release date is published; the pinned commit gives the same reproducibility.
